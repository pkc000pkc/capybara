# Capybara Workbench UI 回归报告（2026-11-14 第四轮：业务链路）

本轮在第三轮修复后的应用中，按测试用例 H01-H06 逐项从页面发起业务场景。测试过程中不修改代码；发现阻塞后停止继续点击，先保留失败证据。

## H01 股票投资方法调研

### 操作

在新会话发送：

> 请调研关于股票投资的方法，使用浏览器或市场研究能力获取至少两个公开来源，列出来源、日期和不确定性。只做调研，不下载文件、不修改项目。

### 页面可见结果

- Agent 确实调用了 `browser_read`，随后调用多次 `read_runtime_artifact`。
- 执行时间线显示模型阶段、工具名、callId、耗时、工具结果回传模型等步骤。
- 某次 `browser_read` 明确显示：`{ "code": "INVALID_ARGUMENTS", "message": "page returned HTTP 404" }`。
- 经过 12 次工具调用、21 步后，消息失败，页面显示：

```text
model input requires 14019 tokens but the configured limit is 14000; only builtin.cache is compressible
```

### 结果

**失败。** 工具调用和证据时间线可见，失败原因也可见，但没有得到调研结果。浏览器结果持续写回上下文，最终超过模型上下文限制。

## 错误态恢复验证

在 H01 失败消息上点击“停止本轮”：

- 页面仍显示“工作中”；
- 状态栏仍显示“正在等待模型输出”；
- “停止本轮”仍可见；
- 再点击“新会话”没有切换出可用的新会话。

### 结果

**失败，缺陷 R4-01。** 失败后的 RuntimeLoop/前端状态没有回收到可发送状态，阻塞了同一项目后续业务场景。

## H02-H06

本轮没有继续对 H02 下载研报、H03 日线数据、H04 Python 分析、H05 看板部署、H06 交易建议执行实际操作，因为 R4-01 使当前项目无法创建和切换到可运行的新会话。继续点击不会产生有效的独立测试证据。

## 新增缺口

1. **工具结果上下文治理不足**：浏览器调研在多轮 `read_runtime_artifact` 后将输入推到模型上限，缺少及时摘要、裁剪或预算门禁。
2. **失败态回收不足**：模型输入超限后，消息虽显示失败，但运行状态仍为工作中，停止动作没有终止挂起状态。
3. **失败后会话隔离不足**：运行状态未回收时，新会话按钮不能建立可用测试上下文。
4. **浏览器错误恢复不足**：`browser_read` 的 HTTP 404 已进入时间线，但 Agent 继续重复读取，没有快速切换到替代来源或向用户说明来源不可用。

## 下一轮修复目标

先修复 R4-01 的错误态回收，确保以下条件同时满足：

```text
模型/工具失败
  → 消息标记 failed
  → run 状态回到 idle/waiting
  → Stop 按钮消失或变为不可用
  → 可以创建新会话并再次发送
  → 失败轨迹仍可回放
```

随后再单独回归 H01-H06，并将上下文预算和浏览器 404 处理作为独立验收项。
