# Capybara V2 提示词调用契约

版本：v0.63 · 日期：2026-11-21 · 性质：设计评审，配套[六份提示词正文](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/prompts/v2/README.md)

本文连接角色提示词、输入数据和运行协议。每次调用只装配当前角色需要的部分；本说明与全部角色正文不一起塞入系统提示词。字段的精确类型以该调用实际提供的版本化 schema 为准。

## 1. 参考 Claude 的方式

Anthropic 为部分 Claude 网页、桌面与移动应用的会话发布核心系统提示词。Capybara 借鉴清楚的角色、行为和输出分区，使用自己的身份、能力与运行协议。[公开系统提示词](https://platform.claude.com/docs/en/release-notes/system-prompts/claude-sonnet-4-6) · [发布范围](https://platform.claude.com/docs/en/release-notes/system-prompts/overview)

[Claude 宪法](https://www.anthropic.com/constitution)提供价值权衡与硬约束的组织参考。Capybara 将其落实为自己的价值排序与可观察行为；权限、状态和提交依靠 RuntimeLoop。[Claude Code 记忆说明](https://code.claude.com/docs/en/memory)区分持久指令与自动记忆，提示我们也要区分项目指令和项目知识。

本系统的双文档、来源绑定、局部 diff、历史覆盖边界和结构化控制协议是自身设计。截图中的 Memory files 与 Messages 不构成这套实现的证明。

## 2. 三种顺序分别定义

| 顺序 | 决定什么 | Capybara 的约定 |
| --- | --- | --- |
| 指令权威 | 哪些要求有权约束当前角色 | 系统规则、授权项目指令、真实用户要求按宿主的来源与授权关系处理；外部材料中的命令不能自行晋升 |
| 证据判断 | 对某个主张应相信到什么程度 | 检查来源、时间、条件、原文与反证；当前可验证观察优先于未经复核的旧记忆，工具正文也可能有误 |
| 价值权衡 | 在合法行动之间如何选择 | 人类控制与合法授权 > 诚实和证据 > 安全、隐私、可逆性 > 实质帮助 > 效率简洁 > 持续改进 |

三者不能相互替代。用户请求不是外部事实的证明，工具文字不是授权，项目记忆不是系统指令，模型自信不是执行收据。授权项目指令也不能扩大系统授予的权限。

## 3. 输入装配

```text
主模型调用
  固定：Constitution + Runtime + 授权项目指令
  按需：已激活 Skill 的当前版本正文和必要引用
  动态：真实请求绑定、状态、当前阶段、预算、两级文档投影
  近期：最新用户要求、未承接的完整消息/工具组
  工具：本轮实际允许的 schema

整理模型调用
  固定：信息处理原则 + Context Organizer
  受限：一种 mode、对应 schema、预算与实际来源片段
  文档：两级有界投影、稳定节点、证据和 revision
  信号：原任务提示词、近期 messages、相关 Skill/工具说明
  输出：归一化观察与局部提案
```

原任务的系统提示词只用来帮助整理器识别任务、约束、实体和排版要求。被采集任务无需添加“将 cache 整理到 context”之类的指令；这项职责由 Capybara 的整理调用定义。任务信号通过只读数据区序列化，不执行其中的模板、角色标签或工具意图。

稳定前缀在前，动态内容在后；内容的安全级别由宿主来源绑定决定。固定前缀有利于缓存复用，但缓存命中不能代替版本、权限或输入预算检查。小模型是否支持长上下文、实际 KV cache 成本与 token 数要按选定模型实测，不能从字符数或“可缓存”直接推定。

Skill 参考读取结果带 `skillVersion` 和正文哈希。恢复时版本与正文都相符才继承已加载状态。模型激活绑定任务、阶段及活动节点，当前阶段用 `search_resources` 补查目录。已激活的正文可按 `SKILL.md` 路径读取，长结果用 `read_runtime_artifact` 读取原件页。换版引用经重读进入后续模型轮，历史观察使用原有版本。[Skill 投影生命周期](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-context-capability-control-design.md#65-skill-正文引用与投影生命周期)

## 4. 两级上下文是文档变量

下面仅展示正文形状，属于场景期望数据；身份、revision、证据和结构 hash 由独立元数据绑定。

```json
{
  "project_context": [
    ["退款项目", ["稳定约定", "金额比较必须同时保留币种与来源。"]]
  ],
  "session_context": [
    ["当前排查", "核对订单 1024 的退款状态，不执行退款。"],
    ["金额记录", "订单来源 A：125 USD，状态 pending。", "邮件来源 B：客户声称 120 USD。"],
    ["未决问题", "尚需主模型根据原件判断两条记录是否描述同一笔金额。"]
  ]
}
```

两个变量的正文分别符合递归 `List<List|string>`。稳定节点映射供 diff 与折叠使用；展示采用文档缩进与折叠，不能用嵌套元数据对象的整段 JSON 代替正文。

项目约定进入 project 之前，要具有真实项目锚点、长期有效性和来源依据。订单号、当前查询和等待状态不能因示例并列出现就晋升。训练冻结的项目文档只读，会话文档仍承接当前解题信息。

`runtime_state` 是独立的控制快照。文档可以引用观察过的进展，却不能靠编辑一句“子任务已完成”改变子任务状态。两级文档也不吸收全部消息、工具定义或 Skill 正文。

## 5. 每种角色的一次调用

| 角色或模式 | 调用前提与主要输入 | 模型输出 | 宿主后续动作 |
| --- | --- | --- | --- |
| 主轮 | 当前请求绑定、状态、知识、近期要求与实际能力 | 一种控制决策或指定的原生工具意图 | 校验绑定、能力和状态后执行；下一轮使用新快照 |
| Normalize / Organize | 完整工具组已结算，取得有界原件片段与两级文档快照 | 观察、局部 diff、归档和覆盖建议 | 登记真实来源；校验、提交并持久化后推进覆盖边界 |
| Recall | 有明确的信息缺口及实际检索候选 | 相关候选 ID 和理由，或查询建议 | 检索/读取由真实能力执行，召回材料重新进入候选 |
| Parent Merge | 父层已核实子身份、终态及原件引用 | 带来源的父文档候选与补证据建议 | 独立记录父层消费，再按普通 diff 门禁提交知识 |
| Reflection | 有实际错误回执与剩余预算 | 诊断、纠正计划、候选 diff、证据请求和重试前提 | 主轮重新决策；错误历史与旧回执保持原样 |
| Dream | 有受控空闲窗口与版本化快照 | 重组、去重、归档、记忆候选等普通提案 | 按相同版本和证据门禁审核；前台更新后复核 |
| Child | 有父层授权、局部目标、能力与预算 | 子任务控制意图、结果、原件与未决项 | 宿主确认子生命周期并组装证据包；父任务单独判断 |

Normalize、Organize、Recall、Parent Merge 与 Dream 可以由同一个小模型承担。每次调用明确一种模式与允许字段；共享权重不等于共享执行权限。辅助角色需要更多材料时提出证据请求，不能自行获得主代理工具。

整理器保留“来源 A 主张 X；来源 B 主张非 X”以及各自条件，不给业务主张签发真伪结论。Parent Merge 的来源可用性审核也不能把子代理意见自动提升为事实；业务判断始终由主模型承担。

桌面召回命令、`recall_context` 工具与运行时共用 20 条结果上限。查询文本最多 256 个 UTF-16 代码单元，作用域为 `project`、`session` 或 `both`。工具的可选 `source_kind` 对应命令的 `sourceKind`，可取 `source_archive`、`information` 或 `candidate`。宿主在排序与可选模型审查前过滤来源。指定归档原件时，如无授权范围内的归档命中就返回空列表。命中随原件引用进入当前会话候选。

## 6. 主轮的状态决策

| 当前条件 | 允许提出的意图 | 必须由运行时确认的结果 |
| --- | --- | --- |
| 尚有独立、可执行工作 | `tool_call` 或携带具体 `reasoningNextStep` 的纯推理 `continue` | 当前阶段、权限、重复待办、预算及真实执行结果 |
| 需要拆解或修改依赖 | `propose_plan` | plan revision、无环依赖、保留既有义务；计划接受不授予权限 |
| 某些分支缺少必要人类输入 | `ask_user` | 可见问题、真实 humanRequestId、受阻节点与回复关联 |
| 活动节点缺少可核验材料 | `continue` 加 `evidenceRequests` | 按节点与来源登记，分别接收并保留待审核材料 |
| 活动分支或根任务等待真实条件 | `wait`，局部等待提供 `waitSpec.blockingTaskIds` | 真实订阅、关联 ID、宿主期限、超时/取消与恢复 |
| 知识文档需要更新 | `propose_diff` | 作用域、来源、可见节点/hash、revision、持久化及投影回执 |
| 有失败且需要纠正建议 | `reflect` | 反思预算、输入快照与输出审核；不重写原历史 |
| 活动节点已取得完成条件所需的回执 | `complete_plan_nodes` | 当前计划修订、活动节点、原义务与回执归属 |
| 全部完成条件已有依据 | `finish` | 整个任务账本、必需动作/证据、人工请求、等待、未知副作用与子结果消费 |

这些是设计语义，每轮只能从宿主实际给出的 allowedDecisions 选择。局部分支受阻只阻塞依赖它的节点；全局暂停是否允许由调度器判断。一次模型回答结束、run 结束、子任务完成、父任务完成与 session 结束分别管理。

纯推理 `continue` 使用 `reasoningNextStep`，用户结果留给 `finish`。宿主以实际能力、阶段和知识修订识别相同任务快照中的重复待办，保存被拒回复，并在已有输出修复预算内请模型重新选择。补证据的 `continue` 按原证据请求登记。`reasoningNextStep` 在其他决策中作为无控制效力的元数据留存。

`RUNTIME_COMPLETION_CHECK_SCHEMA` 指向完成检查的必填字段与形状，`RUNTIME_COMPLETION_CHECK_TASK` 指向当前任务绑定，`RUNTIME_COMPLETION_CHECK_BLOCKED` 指向实际阻塞或应随结果报告的不确定性。宿主只用固定说明装配修复反馈，并保存待修复原响应。多模型流式通道把待修复响应交给宿主，用户结果在验证通过后发布。完成仍经过同一账本校验。

`RUNTIME_COMPLETION_TRANSPORT` 用于当前允许完成、模型却只返回单个未投影原生 `finish` 调用的情况。宿主留存原响应，用现有输出修复额度请求新的控制 JSON，并从当前绑定核验 `completionCheck`。修复轮继承真实工具结果与已登记义务。

同样的修复适用于本轮允许的其他单个控制意图，包括 `ask_user`、`propose_plan` 和 `propose_diff`。修复要求模型按目前的 `output_schema` 重新提交。原生调用中的参数只用于审计，实际状态变化由新 Envelope 核验后提交。

对于使用 Chat Completions 控制载体的提供方，若活动 `execution` 节点的能力列表为空且本轮允许 `propose_diff`，同时提供 `submit_capybara_control` 和已投影的观察工具。载体沿用当前 `output_schema`，单独提交一个信封，模型依据两级已有文档投影定位目标。载体与其他工具同批时，宿主拒绝且零分发，修复说明分别使用控制通道或观察工具。已提交编辑仍经过独立的节点回执核对。

DeepSeek Chat Completions 在文件证据核对、已提交编辑核对、子代理目录核对、已有计划复核及相关修复中可单独提供 `submit_capybara_control`。参数只携带一个版本 2 的 `envelope`，宿主从实际传输响应解包后按原绑定、决策、证据和文档校验。可执行能力投影为空。载体与原生调用混合时拒绝整批，实际请求和响应纳入用量与审计。子代理目录核对后的完成仍引用真实 `search_resources` 回执。

请求验收尚未活动的节点时，结构化信封和误用的原生调用都保留拒绝。若当前仍有活动节点，有界修复轮给出其身份和所需能力，沿真实阶段投影继续剩余动作。现有子结果、工具收据和计划版本保持原始归属，修复不能结算其他阶段的节点。

用户明确要求先提出人工问题，并在等待回复期间继续已经获准的工作时，在计划列表中将人工节点排在最前。`dependsOn` 给确实需要前置节点完成的动作使用。独立工作的依赖不包含该人工节点。评审时检查问题已登记、活动子节点获得自身授权、交付仍受原人工回复约束三项事实。

同一个响应把一项允许的控制决策误投为多个同名原生调用时，整批拒绝并保留原始材料。修复使用一个绑定当前请求的信封。文档编辑按顺序放在同一个 `candidateDiffs` 数组，依次核对活动节点、候选证据与文档版本。若还需要新节点，先提交计划修订。混入外部动作或使用互相不同的控制决策时，沿用批次冲突或工具拒绝。

直接阶段在当前运行中可凭已验证的部分发布或超过批次预算的完整多文件读取触发一次文件核对。若上一轮用户可见答复已经完成，后续直接请求也可核对实际投影中仍有有效证明的发布内容，或当前会话仍完整可见且通过原件校验的原始多文件批次。`finish` 仅使用本次成功动作，历史原件可作为证据来源。缺少事实、原始行或新动作时用 `continue` 说明实际缺项，下一轮恢复工具投影。

核对轮的 `finish` 引用未登记证据、缺失动作或无效引文时，修复输入保留答复草稿和已见真实证据，继续使用控制投影。草稿只供核对，重新提交的结果仍须通过本轮所有验收条件。

原生批次同时携带一个允许的控制意图与本轮已投影的工具时，整批以 `RUNTIME_ACTION_TRANSPORT_CONFLICT` 拒绝。修复轮保持当前阶段能力，要求独立提交工具或控制信封。批次含未投影工具时继续按权限拒绝。允许完成时，独立的业务 JSON 对象或数组可作为答复草稿进入无工具修复，仍需新 `finish` 信封通过完成检查。

发布 schema 带本次完整的 `binding` 常量。相同会话、任务和运行的过期请求进入有界重提，并由宿主再次校验当前请求和状态。纯推理也受此约束。原输出保存在审计原件中。

信封顶层字段按严格 schema 校验。API 请求的格式字段进入信封时，宿主用 `RUNTIME_CONTROL_UNKNOWN_FIELD` 指出可安全显示的多余字段名，通过无工具、有界修复要求重新提交。修复前无状态变更。

结构化逐字引文可用 `fileQuotes` 的 `evidenceId` 引用本次发布的文档证据，或用 `scope: "session"` 和 `readArtifactId` 引用模型实际看到的文件行。直接读取使用 `read_file` 的 `runtime_receipt.resultArtifactId`，文件行分页使用页内 `result.artifact_id`。宿主核对行页成功回执、页原件和文件原件。目标同级字段须有 `file` 与 `line`，原行须同时出现在实际请求和持久记录中。JSON Pointer 的 `target` 指向 `userMessage` 中的 `null` 或等待核对的完整 `quote` 原行。

请求 schema 把 `planProposal`、`planProgress`、`candidateDiffs`、`waitSpec`、`completionCheck` 和原生通道上的人工 `actions` 绑定到对应的 `decision`。其余分支使用 `null` 或空数组。无该决策的阶段直接限制载荷为空。宿主仍校验通用 Envelope 和实际状态。互斥载荷错误以 `RUNTIME_CONTROL_PAYLOAD_CONFLICT` 进入同一运行的有界修复，指定冲突字段及应使用的值。原响应保留在审计原件中，提交前不产生计划、等待或工具记录。

原生调用的 JSON 参数解析失败时，模型适配层保留调用名称、批次大小、原参数和实际用量。宿主仅对当前允许、没有被投影为工具且独占该响应的控制决策启动控制修复。修复请求无原生工具，沿用原任务并提供新绑定。错误原参数留在原件。真实工具或混合批次的畸形参数由模型协议拒绝，整个批次不会进入执行队列。

计划委派单独调用 `delegate_task` 并提供活动节点的 `plan_task_id`。规划声明委派能力和所需只读能力，实际请求只授予其中授权的子能力。只剩待处理子句柄时进入 `delegation`。节点验收依据真实子结果与审核回执，已有凭据的接管路径仍须验证接管后的父动作。派发失败不产生子句柄，原节点保持待处理并保留已登记的委派要求。

子代理的唯一授权为目录查询时，同一运行收到首个精确匹配的成功回执后，安排一次无工具的 JSON 核对轮。模型可凭当前真实回执提出 `finish`，或者用 `continue.reasoningNextStep` 说明缺项并在下一轮恢复原查询能力。完整约束、预算、完成门禁和父层审核继续生效。

`read_child_result` 保持原结果 hash 和工作包引用，另以 `output_excerpt` 提供有界交付正文。读取下一段时提交同一 `child_id` 与前一页的 `output_next_offset`，宿主按页返回新的读取回执。核对本地子任务动作时，使用真实 `local_evidence`。缺少交付正文时优先读取交付正文页；工作包及原件能力供后续审计或深入补证。

成功的子结果读取和审核动作以 `completionPlanTaskIds` 表达验收归属。宿主以实际子句柄核对原委派节点。明确获授该审核动作且当时活动的专用审核节点也可取得动作引用。`activePlanTaskIds` 记录当时的投影，旧回执沿用原字段验收。

无工具修复仍收到服务商调用标记文本时，保留原文并转为 JSON 控制修复。真实动作仍只从正式原生工具通道执行。父层已接受子结果且其余条件满足时，委派节点的 `planProgress` 可以使用空的 `actionRefs`、`evidenceRefs`，宿主继续校验已有义务。

计划修订保留已接受节点、义务与引用。宿主拒绝新加入的失败动作、不可核验动作与其他节点的回执，并指出引用应从哪个节点移除。已有计划的独立复核可用 `resume_plan` 和本轮绑定确认继续原计划，控制载荷为空。宿主推进状态修订，保留原计划修订、节点、义务与等待。新成功动作按恢复后的活动节点验收。

已有计划可用 `propose_plan` 与 `planAmendment`。将 `planProposal` 设为 null，按真实 `basePlanRevision` 提供 `addTasks` 或 `updateTasks`。`updateTasks` 只允许待执行节点，并分别用 `addCapabilityIds`、`addDependsOn`、`addCompletionConditions` 追加。`addTasks` 表达新节点的目标、依赖与能力，宿主初始化为空回执的 pending 节点。宿主将变更展开到权威计划，沿相同门禁验证引用、环、权限和运行状态，再一起提交。追加并不自动执行动作或授予子任务权限。

同一运行、用户输入、计划修订、阶段和活动节点组已用 `resume_plan` 结束复核时，重复请求独立规划进入有界控制修复，零工具分发。主轮可凭回执验收节点、直接提交必要的 `propose_plan` 或说明具体补证需求。能力检索对主代理按名称或 ID 返回当前目录状态。`outside_current_projection` 表示已注册而当前阶段未投影，`child_state_required` 表示父层生命周期动作缺少相应子任务状态。

人工回复、等待唤醒与子结果返回都只触发新判断，不证明业务已成功。取消、失败、预算耗尽与成功使用不同原因；旧格式的 completed 也必须经过同一完成门禁。

已接受计划仍有待验收节点时，当前阶段和 schema 均收起 `finish`，`completionCheck` 使用 null。活动阶段的提前完成提案保留为审计记录。只有待验收节点构成阻塞时，宿主在原额度内提供活动节点 ID 和当前工作提示。原计划和已登记义务继续由账本承接。节点准备和验证交付材料，验收后的 `finish` 负责发布最终答复。

局部人工请求有回复后，`runtime_state.branchHumanReplies` 显示最近的真实回复回执。`replyMessageId` 定位原答复，`taskIds` 给出原绑定，`completionActionRef` 用于该节点的 `requiredActions`。宿主从同一 session/task/run 的已满足订阅和实际用户信号核对引用。答复可以是同意、拒绝或进一步限定，模型按实际内容决定后续动作。

单独的授权、确认或选择使用 `phase: "human_input"` 和空 `capabilityIds`。问题只绑定当前活动的人工节点，登记后由宿主继续调度独立工作。答复到达后，`complete_plan_nodes` 以绑定的 `human:` 回执验收原节点，各项业务权限仍由宿主分发校验。回复新增的文档编辑用 `propose_plan` 纳入执行节点，作为交付前置依赖。

计划轮的 `ask_user.blockingTaskIds` 枚举来自当前任务状态。已经阻塞的节点由其原请求承接。模型重复针对这些节点提问时，宿主在登记或发布正文之前拒绝该意图，保留原等待，并在修复轮列出可继续的独立节点。整轮阻塞可按当前投影绑定根任务。

`ask_user` 提供一条实际展示的 `userMessage` 和一项 `ask_user` 动作。两处使用同一个提问。输出 schema 拒绝空白的 `userMessage`，控制信封校验也指出缺失字段。修复使用当前绑定和原定 `blockingTaskIds`，问题仍经正常登记条件处理。

计划已存在时，提问和等待的 `blockingTaskIds` 可写局部节点列表，或单独写整个运行的根任务 ID。混用时，宿主保留已有订阅与问题，拒绝本轮提案并给出活动节点。不产生新订阅、不重复展示原问题。

`capybara.human.reply` 和 `capybara.evidence.observed` 由宿主创建订阅。模型重复以 `wait` 登记这些事件时，宿主保留原订阅，按有限额度要求模型验收已有回执或继续分支。只剩受阻节点时由调度器暂停。

初次规划与重规划均校验新增动作和证据引用，包括待执行节点。`requiredActions` 使用当前运行的成功回执，`evidenceRefs` 使用已登记证据。将未来产生的回执写作完成条件。拒绝时原始响应随审计保存，修复输入给出拒绝原因和当前绑定。重提沿用宿主提供的原计划修订和已登记义务。兼容要求 `tool:<name>` 需要目录中有真实注册，最终仍核对工具的真实成功。

`decision: "complete_plan_nodes"` 携带 `planProgress: { basePlanRevision, nodes: [{ id, actionRefs, evidenceRefs }] }`。本轮 schema 固定当前修订并枚举 `execution.activeTaskIds` 中可验收的节点。`planProposal` 为 null，`evidenceRequests` 与 `uncertainties` 为空数组，每个节点 ID 只列一次。宿主将新回执并入原义务，保留已登记的证据请求和不确定性。需补证据或新增不确定性时另选允许的控制决策。`recentPlanActions` 提供当前活动节点执行时生成的成功工具回执。人工、文档编辑、子结果和父层接管分别使用原有真实绑定。人工阶段修复错误节点时只提交当前控制信封。需要调整结构或依赖时另提 `propose_plan`。

计划节点的 `capabilityIds` 使用当前能力目录的注册 ID。执行所需且有权限的能力即使标为 `not_loaded`，也应先写入对应节点，在节点活动时加载。加载成功后仍缺少节点声明时，用 `propose_plan` 修订原节点并重新投影。文档编辑可以使用空能力数组，完成条件指向可核验的文档、动作或证据。首次规划且账本无成功动作时，schema 要求每个节点的 `requiredActions` 为空。修订保留原义务，新动作引用由宿主复核。用户报告由 `finish` 交付，前置节点的授权、委派审核与编辑回执由 `dependsOn` 承接。未知能力 ID 或不匹配的回执由宿主拒绝，在原预算内重新提交。

发布的 schema 固定当前计划修订与可绑定的活动编辑节点。执行阶段收到同一组节点、顺序、状态、依赖和义务时，保持原修订。仅改写目标描述也沿用原计划。宿主返回活动节点及可继续的操作。显式规划轮允许重核同一执行图并转回执行。

有足够证据且允许 `finish` 时，主轮直接交付。初次提案把未获真实回执或证据的普通节点标为已完成时，宿主要求修正：复制当前已有且实际符合条件的凭据，或维持该节点待处理。

切换阶段后，当前未投影的批次若被同次运行已验收的 `project-files:read_file` 原件覆盖，宿主拒绝分发并提示使用可见结果和原回执。精确重复可按参数证明，子区间按已核验原件的路径、编号和行范围证明。若活动节点已取得文档提交回执，修复轮提供其 `context:` 引用用于节点验收。其余越界批次沿用分发拒绝。工具和完成义务以当前投影为准。

计划执行阶段有活动节点时，每项模型文档 diff 必填 `planTaskId`，取值为当前 `activeTaskIds`。宿主在写入前拒绝漏填项并给出有界控制修复。没有覆盖该修改的活动节点时先修订计划。运行时从实际提交回执生成 `context:<receiptId>`。下一轮用 `complete_plan_nodes` 引用该回执验收原节点，随后执行新投影中的依赖节点。回执归属随 SQLite 提交保存，重放、回滚与核验类回执可独立追溯。

纯文档节点组刚提交真实编辑时，宿主从持久账本读取上一个模型请求产生、仍归活动节点的回执，给出一次控制核对。原完成条件和权限继续生效。缺少动作时用 `continue`，追加文档修改时可用本轮控制提案。历史回执重放和回滚批次不触发此核对。

召回内容通过 `add_entry` 回填时，`headingPath` 表达从根开始的目标路径。用户只命名新章节时使用单层路径；已有唯一同名章节时复用树中的完整路径。提交回执中的路径参与交付验收。

验收 schema 按活动节点排除已发布且确定属于其他节点的动作回执。宿主根据当前运行的成功工具、人工和编辑回执重新检查归属。拒绝时保持当前修订，反馈列明该节点的已识别错误引用及各自归属。下游节点通过 `dependsOn` 承接已验收的前置工作。仅核验材料时可用 `actionRefs: []` 和实际证明条件的登记证据。未覆盖的编辑先纳入当前计划，纯答复在所有节点验收后由 `finish.userMessage` 交付。

工具轮用尽时报告 `budget.usedToolRounds` 与 `budget.toolRoundsExhausted`，实际请求的工具数组为空。宿主继续按当前活动节点和已取得的证据处理控制信封。只有已经满足的任务才能完成，超额调用须在分发前拒绝。

活动节点再次提交单项新增条目时，若当前投影里的条目、正文、章节、候选来源及证据与原持久化结果一致，宿主返回原节点的 `completionActionRef` 供模型重新选择控制决策。模型仍需核对节点条件后提交验收。不同内容或目标沿用普通提案校验。

未知 MCP 写入出现在 `runtime_state.mcp.pendingOperations`。从宿主状态取得 `operationId`，按本轮权限加载并投影配置的只读核查能力，再调用 `verify_mcp_side_effect(operation_id)`。模型只提交操作 ID。运行时核对实际 RPC 和终态回执，`applied` 证明原动作，`not_applied` 允许按授权提出新动作，`unknown` 继续阻塞。[MCP 核查合同](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-mcp-runtime-design.md#41-核查未知写入)

宿主已启用轮询且核查能力在本轮投影时，主轮可用 `runtime / mcp.operation.settled` 等待同一根任务的一条操作，引用宿主期限。恢复轮可用 `read_wait_signal` 读取终态回执。信号满足仅表示核查已有明确结果，原任务仍走完成门禁。[MCP 结算等待](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-mcp-runtime-design.md#43-等待写入结算)

MCP 人工表单的实际请求由宿主签发 `requestId`。仅当主轮投影含已登记的表单时，装配 Runtime 中的 `mcp-form` 说明。模型使用 `runtime / mcp.input.responded` 等待一条已登记请求，并以 `resume_mcp_input(request_id)` 提议续传。宿主从私有记录取出原参数、状态和经用户提交的回复，绑定当前投影中原能力。一个回复只允许消费一次。模型看到请求状态和终态工具结果，结构化用户回复不经聊天或知识文档。[MCP 人工输入](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-mcp-runtime-design.md#44-人工输入往返)

URL 输入在主轮中使用 `hasUrlInput` 标识。待回复的请求附带使用真实 ID 的 `waitSpec`。只有用户在工作台提交回复才产生等待信号，导航和外部凭据交互由系统浏览器承接。接受回复省略 `content`，续传以实际服务输出判断是否继续或完成。[URL 控制契约](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-mcp-runtime-design.md#47-url-人工协助的控制契约)

带 `operationId` 的表单全部接受后，模型单独调用 `resume_mcp_write_input`，宿主复核原写入的阶段和授权并预登记新的 RPC 尝试。拒绝或取消关闭本地表单，等待回执保留原操作 ID 和用户决定。远端结局仍通过原操作核查。[写入确认](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-mcp-runtime-design.md#45-写入确认与续传)

带 `workflow` 的表单在原节点等待。模型处理表单获得终态结果后，从 `workflowRecoveries` 读取 `inputReceiptId`，单独传入 `resume_workflow` 的 `input_receipt_id`。宿主核对原图、节点、任务和结果哈希，按当前投影继续剩余步骤。写入结果仍未知时走原操作核查和 `verification_receipt_id` 路径。[Workflow 人工输入](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-mcp-runtime-design.md#46-workflow-节点的人工输入)

Workflow 核查后按 `workflowRecoveries` 的真实 Workflow ID 和回执单独提交 `resume_workflow`。运行时保留已完成步骤和迭代，按当前授权调度后续节点。下游缺原始输出时，仍用原 operationId 从登记的只读工具补读。[Workflow 恢复](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-mcp-runtime-design.md#42-恢复-workflow)

## 7. 异步子任务的父层行为

父层从实际工具定义限制委派目标与子结果范围。目录查询验证能力登记，业务原件由获授原件读取的节点处理。父层用 `child.ready` 等待时复制子 `waitRef`，局部等待只绑定该子句柄对应节点。人类请求使用自己已登记的订阅。关联值与事件不匹配时，宿主拒绝本次提议，并在有界修复里保留原计划和运行状态。

子模型误用普通正文交付结果，或把 `finish` 误投为原生工具时，宿主通过空工具投影请求一个符合本轮 schema 的控制 JSON。模型可把原结果写入 `userMessage`，引用实际成功动作。原响应继续作为诊断材料。修复使用新请求绑定和原任务账本，父层只能在子完成门禁通过后审核成功结果。

已发布给子模型的成功目录搜索回执可继续作为任务依据。整个批次只重复当前目录中同样的搜索结果时，宿主在分发前拒绝，单轮只投影控制 JSON。该轮可以引用原成功回执完成，也可以指出剩余缺项。宿主比较当前目录结果和原始可见结果，保留不同查询或目录变化后的正常执行。

```text
真实委派句柄
  → 父层推进独立工作，或等待真实子信号
  → 读取与句柄、结果 hash 对应的来源
  → 父层审核并记录消费
  → 需要的知识形成候选 diff
  → 父层重新检查完成条件
```

读取、消费、知识提交分别留痕。消费的 accept 表示父层已审核如何使用该来源，不表示其中每条主张已确认；conflict 表示保留分歧，needs_more_evidence 表示仍有缺口。失败、取消和超时结果也需要父层明确处理，不能用删除子记录消除完成义务。

结果读取回执由宿主在实际读取后签发，审核引用实际结果 hash；父层不能在看到结果之前预先构造已消费证明。子代理请求补充输入时，回复关联真实子请求，再观察新的状态/信号。迟到结果作为补充原件留存，不把已超时或已取消的终态改成成功。

成功的本地子结果可附 `local_evidence`。宿主核对结果包哈希、真实子身份、成功步骤、工具观察和对应原件，再提供最多八条工具回执引用及总数。引用属于子运行。短原件正文通过长度和完整哈希校验后随回执提供。父层用这些信息审核局部交付，缺少具体材料时从原件分页补读。外部宿主的证据通过其原结果包提供。

子模型把原件 ID 写入 `requiredEvidenceRefs` 时，宿主验证当前文档登记。可修复的误引保留原候选答复正文，使用空工具投影及新请求绑定重提。成功动作引用使用 `requiredActions`。

如果父层决定接管已拒绝或冲突的节点，在单独一轮调用 `take_over_child_task`，使用实际 `child_id`、`plan_task_id` 和 `review_receipt_id`。接管后的 `execution.parentTakeover` 由宿主提供。执行当前节点允许的工具，再将至少一项已成功且属于本次接管的动作加入 `requiredActions`，沿用原完成条件提交计划更新。接管原因和子结果审核继续各自留痕。[父代理接管协议](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-child-runtime-design.md#41-父代理接管)

具体工具名称、字段、信号类型与可用性以本轮 schema 为准。本设计约束不能代替异步服务、权限与关闭恢复测试，当前验收状态统一回到[缺口清单](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-context-capability-control-design.md#47-本次核查的证据边界)。

## 8. 稳定结构化输出与总预算

主轮 `propose_diff` 的可选 `classification` 在提示词与解析器里使用同一分类 schema。填写时要带 `durability`、`target`、`confidence`、`reason` 和 `projectAnchors`。会话资料可省略整体分类，或明确 `projectAnchors: []`。跨会话项目晋升仍须核查实有项目锚点及来源证据。格式拒绝引导重提，不消耗已取得的候选或回执。

`add_entry` 使用实际章节路径及候选正文，缺失章节随正文提交一次创建。`add_heading` 等结构操作须在 schema 中提供 `diffVersion: 2`、当前可见 `target.nodeId` 和 `targetNodeHash`。结构绑定错误的修复提示分别说明正文写入和空章节操作所需字段。

结构正确分四层保证：提示词定义语义，schema 约束形状，语义门禁验证来源/权限/版本，事务与回执证明提交。任一层失败不执行未经校验的动作、不应用部分 diff、不推进覆盖边界。结构修正只在有限预算内进行；修复过程不能补造来源或权限。

主轮的工具动作使用 provider-native 函数通道。宿主给该轮投影控制 schema 时，决策枚举排除工具动作并按当前阶段收窄，`actions` 只表示人工问题。整理轮使用 Organization schema，反思使用独立 Reflection schema。字段、空值、枚举与模式按实际 schema 输出。

无工具的模型请求启用供应商 JSON 输出选项。投影了原生工具时，由实际工具通道和版本化控制 schema 共同表达两种可选输出，宿主继续校验控制 Envelope。规划目录优先提供已可用、以及有权限但待加载的工具。计划执行轮显示本次实际投影的原生工具名。

无工具的 JSON 回合返回空白时，有界重提可采用供应商文本传输。请求仍投影空工具列表，使用新请求 ID 和当前账本绑定，完整解析并校验为一个控制 JSON 对象。原空白回应进入审计，状态、材料与权限沿原轨迹。

规划任务中的旧版续轮 JSON、超出当前节点的分支请求和含其他工具的委派批次进入有界修复。混合委派批次中的工具尚未执行。相同计划阶段、工具授权、用户指令及知识修订下，连续纯推理至多三次，随后使用实际工具、必要输入、补证据或计划调整继续。控制提案原件进入运行轨迹。模型的后续轮据 `runtime_state` 读已接受的计划与分支，输出修复提示用于紧接的修复轮。V4 整理把这些控制轨迹与业务观察分开处理。

```text
一次调用输入成本
  = 固定角色与项目指令 + 激活 Skill + 实际工具 schema
  + 状态绑定 + 两级文档投影 + 本次来源/必要近期消息

一次调用上限
  = 输入 token + 输出预留 + 模型需要计入的其他预算 ≤ 模型窗口

整个任务总成本
  = 主轮 + 规划 + 整理 + 检索辅助 + 反思/梦境 + 子任务 + 重试
```

各调用均有自己的窗口限制，并从宿主维护的总预算中计费。来源分片短不代表整个整理请求能放入小模型；必须连同原任务信号、文档、schema 和输出预留一起核算。长期运行靠组织、归档与召回收敛，不能静默截断关键条目，也不能以持续提高 token 上限代替闭环。

配置纯文本辅助模型的聊天分词器时，宿主按实际 HTTP 消息、服务使用的模板和生成前缀核算输入。输出预留仍占用同一模型窗口。超窗的请求在发送和登记消费前被拒绝，原始工具组和覆盖边界继续可用。对接方模型档案和应用条件见[统一预算](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-context-capability-control-design.md#62-统一预算)。

短编号整理协议的 `batch` 绑定当前批次。`sources`、`observation`、`candidate` 和 `target` 各自引用所属数组。文档编号按 `scope` 解释，第一项为 1。运行时还原真实编号、版本哈希和应用 idempotency key，再进行完整 Organization schema、来源、权限、版本及持久化校验。如此生成的宿主绑定仅进入审计与训练溯源。

整理提案的提交结果与历史折叠分别核对。申请折叠时，宿主检查完整工具组的原件是否已进入活跃的带证据正文，或已有原件归档回执。仅改变状态、布局或写入空正文时，事实来源继续留在历史投影。已有正文与本次提取一致时，可以通过补充原件证据承接重复内容。新证据不能凭空把无关正文变成覆盖回执。

原文摘录模式以 `organizationVersion: 3` 选择装配。`observations[].sources` 选出要写入的原句，`edits[].observation` 引用相应观察；内容操作由宿主复用所选原文。归档及不确定项分别表达，冲突及越界编号拒绝。宿主根据每个片段的持久处置决定折叠范围，并在实际主轮请求发出前复核正文见证。

逐项处置以 `organizationVersion: 4` 装配。`choices` 的长度和顺序与片段列表一致，允许 K、A、R。宿主在一个批次里优先保留同一读取原件的完整原句集合。整份拟归档的原件使用新的批次和 `task.archiveReview=true` 单独复核。出现分歧时先保留该原件，提交前再核对是否符合局部归档条件。单份原件跨批时，其 A 初始按 R 保留。

在专用 `file_disposition_batch` 下，整份复核后仍有待核对行，并且同一工具组另外两份不同文件已有带原件证据的活跃正文时，只归档该文件初筛和复核均为 A 的片段。其余原句随原工具结果继续可见。同组正文失效、范围不完整或任一归档凭据失效时，恢复原件行。可见性和覆盖位置按普通局部投影门禁计算。

启用专用 `file_disposition_batch` 时，宿主在初筛完成后才安排分段复核。必须已有同一次读取的活跃正文见证，并存在切分边界以外的 A。每次把该原件的一个窗口重新绑定到新的 `batch`，设置 `task.archiveReview=true` 和 `task.archiveReviewScope=window`。只提交窗口内两次一致的 A。窗口交界两侧的完整行仍由正文或原行承接。缺少同源见证、初筛为 R、复核意见不同或位于边界时，保留原件片段。任何复核返回错误、超窗、超时或绑定无效时，拒绝本次整理提交。初筛与复核均计入原模型预算，处置被门禁改写的原输出保留用于审核。

多个原件分别审核后，宿主依据活跃正文和实际归档回执检查整个工具组的承接。

某个完整读取只留下了归档回执时，同一组至少需要两份不同文件的活跃正文见证才能退出主轮。仅有一份见证时可核对整理提案和存储回执，主轮继续读取整个原工具组。

同一组仍有待核对内容时，两个不同文件的活跃正文见证可支持局部投影。宿主逐行核验证据与回执，发出 `unresolved_lines` 和实际随请求提供的 `contextEntryIds`。`contextLines` 标出这些条目中原文摘录所在的行号。一行有多个片段时，证据仍绑定各自的原文范围。工具调用 ID、原始回执和原件分页保持有效。正文或归档凭据失效时恢复完整行。

同一完整工具轮同时返回文件和子结果等独立材料时，专用档案可先提交文件片段的局部处置。主轮仍接收同一工具组的调用和全部回执，其余结果保留正文。后续通用整理可复用当前任务中仍有效的文件见证，处理其余材料。连续覆盖只有在整组及其之前的历史满足原门禁时推进，推进时仍保留作为文件替代依据的条目。

配置专用文件整理档案时，宿主检查新工具结果是否引入独立信息。`read_runtime_artifact` 以 `offset/limit` 读字符页，或同时给出 `start_line/end_line` 从已核验的 `read_file` 原件读取首尾包含的完整行，两种参数互斥。行范围必须在原件覆盖内，每页最多 32 行，正文最多 2,000 个 UTF-16 代码单元。字符请求 limit 最多 8,000，实际页长及下页指针以结果为准。同会话已核验文件的精确字符页或行页保留原历史和回执。原件失配、跨范围按常规调度。实际请求发出前仍复核两级正文与原件承接。

字符页可投影为 `verified_file_page`，同一原件的重叠片段通过真实 `fromCallId` 指向本次请求仍包含的先前完整字符页，以绝对 `offset` 和 `length` 定位。新片段保留逐字正文，当前工具回执不变。仅在核验原件、原始页、范围与长度，并且投影更小时使用引用。参照页离开投影时发出当前真实页。持久化原页和回放始终保留完整内容。

分页校验覆盖局部处置和已整体承接的文件。整体承接以已提交覆盖记录中的文件身份、活跃条目和正文哈希为依据。专用文件档案下，宿主还核对页本身的持久工具结果及回执。新取得的原件行页保持全文。跨运行投影时，局部处置证据经复核后，可从旧行页省去已得到全行承接的行，同时携带原回执、原件身份、已发布条目和未处置行。原页原件仍持久保存。任一凭据失效即回到完整页。高压力时，单独新增已核验页不会重试已送审业务包。

按行补读使用原始 `read_file` 的原件 ID。分页结果中的 `result.artifact_id` 指向原件。把分页回执当原件时，只有经同会话来源和正文校验才能指出原件 ID，该次按行调用仍返回拒绝。范围超限时返回从授权原件计算的有效首段范围，供模型纠正参数。宿主识别出的分页参数反馈，以及逐项匹配活跃正文和来源的完整召回复本，保留工具组和审计轨迹，Organizer 跳过重复处理。归档命中、截短内容、带不确定性的结果继续参加整理。

`artifact_id` 无法解析时，返回 `ARTIFACT_SOURCE_REFERENCE_REQUIRED` 参数诊断。仅在当前请求实际携带同名文件的一份可核验的读取回执时，提示对应原件 ID 和 `source_scope=session`。提示仍是失败回执，后续读取须以新调用通过同一权限和来源检查。原件未发布、回执不一致或存在多个同名原件时，仅返回通用参数说明。文件路径继续经授权的 `read_file.file_name` 处理。

多页文件行范围可以显式传入 `allow_partial:true`。宿主校验整个请求区间在原读取覆盖内，按行数与字符上限取首段完整原行。响应同时提供实际 `end_line`、原请求 `requested_end_line` 和 `next_start_line`。普通行读取仍要求整段能够在一页中返回。

当前阶段未投影 `read_file` 时，匹配已结算的原调查范围可返回原成功回执和原件 ID 供修复。范围匹配绑定同次运行、同一路径、表示方式和持久读取，先前整份读取可用于核对截至当时文件末尾的子区间。原批次不分发。已经提交的当前节点文档变更按原动作回执继续验收，需要新原件时按当前计划重新取得对应权限。

同一运行里，新的整文件读取与已整体承接的原件逐字相同时，可以投影为 `verified_repeat`。宿主同时核验新旧成功回执、完整结果哈希、原件顺序及仍活跃的正文见证。本轮保留新调用回执、原件引用和对应正文。跨运行、精确指定行号或原件变化时仍投影实际读取结果。

两次来源在同一运行内时，形成的引用可继续用于后续轮次及重开后的同一会话。每次装配都复核持久原件、活跃条目和有效正文。后续用户请求中新产生的读取与其他运行的原件分别核验。

V4 的主轮投影使用 `entry-ref` 和 `candidate-ref`。`evidence[].id` 可用于提案的 `evidenceRefs`。普通引用使用 `kind`、`referenceId` 和可用的 `locator`。有界树使用 `capybara:tree` 版本 2，`nodes` 每项按 `columns` 解释，`parent` 和 `children` 是本区从 1 起算的行号。实际 diff 填真实节点 `id` 和 `hash`，局部重排保留隐藏子节点。正文与回放使用已提交顺序，旧投影的对象树保持版本 1。

只有原件、候选和单条证据完全绑定时，文件候选才可缩为 `body=tool_result` 与唯一 `rawArtifactId`。同一次读取的 `resultArtifactId` 用于匹配该候选。专用档案也可对同一请求中发布的其他成功工具结果使用该引用，核对真实调用、持久结果哈希和候选正文。完整的 `load_resources` 继续使用 `body=resource_load_receipt`。当前工具授权由实际投影决定。有其他分类或证据、来源校验失败或原结果缺席时，发送常规候选。持久候选和回放保留原正文与来源。

主轮 `propose_diff` 的每项 `payload.evidenceRefs` 必须是非空数组，引用已绑定候选自身的证据。独立来源分别提出编辑。混用证据时，宿主回滚整批并记录 `EVIDENCE_NOT_BOUND`，在原预算内按当前投影重提。结构操作同时携带 `diffVersion=2` 与本投影的目标节点 hash。提交或拒绝由宿主写入结果审计，并附真实请求绑定。主轮继续时，`runtime_state.recentContextEdits` 仅回传本会话、本任务、本运行的最近八条结果。`applied` 与新投影共同支持模型核对编辑。投影或节点绑定过期时，下一轮读取拒绝回执与最新绑定，在有界输出修复次数内提出新提案。文档回执使用独立结果字段，`completionCheck.requiredActions` 使用实际运行工具与计划的动作引用。

`recentContextEdits[].sourceRequestId` 绑定历史提交。若 `propose_diff`、`propose_plan` 或 `finish` 复制了同会话、同任务、同运行的已知旧请求，宿主拒绝该信封并有界重发当前绑定。修复回合重读当前投影，目标已满足时按原义务申请完成。其他作用域或未知请求 ID 仍按绑定门禁拒绝。

正文回执有章节路径或实际修改的条目时，`recentContextEdits` 提供 `headingPath` 或 `changedEntryIds`。结构回执以目标节点定位，受影响的全部条目留在持久回执中。主轮核对当前投影并继续未完成的义务。`completionActionRef` 只验收原绑定的计划节点。将 `propose_diff` 误发到原生工具通道时，下一轮仍以同一 schema 和当前绑定校验控制信封。响应可使用结构化载体或无工具文本通道，修复沿用原预算。

编辑回执核对轮中，宿主按 `planTaskId` 列出刚提交的 `completionActionRef`。验收夹带其他节点的回执时，以 `RUNTIME_PLAN_ACTION_UNBOUND` 拒绝节点状态迁移。修复轮继续沿用原编辑回执和当次控制绑定，只纠正验收引用。其他节点的原文仍可支持正文，动作回执保留在原节点。确有未办动作时可提交 `continue` 并说明缺项，宿主按后续阶段重投影。

允许 `finish` 的主轮或子轮直接输出未封装的正文时，宿主保留原输出为待验证草稿。修复请求保留原已见证据，使用空工具表和当前绑定，要求把核验后的正文放入 `userMessage`。主轮使用文本传输格式提交控制信封，子轮保持原 JSON 传输及其有界回退规则。仍有必要信息或义务时提交已允许的控制决策，恢复对应的下一阶段。发送用户答复前统一通过结构校验与完成门禁。

宿主在预算内优先发布指令中点名的章节和本次运行刚创建的章节。改名、移动或局部重排的目标已满足时，`recentContextEdits` 中的回执带 `unchanged:true`，修订号保持原值。回执的 `sourceRequestId` 追溯编辑，完成回复选择当前 `request_binding`。训练样本保留该回执与原提案，实际修改才进入 `acceptedOperations`。

文件证据的位置由宿主从原件回执、来源会话、证据哈希和准确片段范围核验得出，完整覆盖掉的工具组也从原件解析。V4 的树结构投影把同一 `kind`、`referenceId`、`file`、`observedAt` 与 `confidence` 的来源只记录一次，放进本区的 `fileSources`。对应 `entry-ref.evidence` 使用原证据 `id`、从 1 起算的 `source` 与原件 `line`。其余证据直接保留来源字段。宿主仍按原 `evidenceId` 校验并引用字符范围，训练和回放保存实际投影文本，原文件和持久化的树保持完整形状。

V4 `finish` 可在 `fileQuotes` 中为最终 JSON 的现有 `null` 字段绑定本轮证据。宿主填入原件证据范围的文字，或逐字核对已经填入的 `quote`。`quote` 与同层的 `file`、`line` 共享一个原件位置。位置不一致时进入 `FILE_QUOTE_REPLY_SOURCE_MISMATCH` 修复。所有引用验证后才发布可见回复，逐项回执写入模型步骤。原始模型响应和提案保留供追溯。

用户要求 JSON 时，`userMessage` 按用户指定的字段交付完整 JSON。普通文字答复直接引用原文，省略 `fileQuotes`。提交 `fileQuotes` 后，普通文字或含围栏、尾注的结构化草稿触发 `FILE_QUOTE_REPLY_NOT_JSON`。宿主按已有额度要求按原交付格式修复，继续保留原任务义务。直接引文的逐字保真按最终可见文本和实际原件核对。

文件批次、整份复核和分段复核共用同一份任务指令视图。宿主先匹配默认模板并复核原渲染，再生成省去执行资源目录的任务背景。只移除与发布资源按原文匹配的系统作者指南。载有 `dynamic_context` 的指南整体保留。自定义模板和无法重现原渲染的项目沿用原指令。切换到标准整理协议的混合批次仍用完整指令。

保留工具组时使用 `contentRef: {field: "lines", numbered: boolean}` 表示逐行正文构成已去掉的重复 `content`。正文引用只出现在保留对应成功读取及原件回执的实际主轮请求中。候选身份和证据引用保持可用，复核原文仍使用原件分页能力。

宿主按父运行记录尝试次数和 token 预留，覆盖主轮、整理、辅助角色和子任务。使用显式额度时，本轮 `runtime_state.budget.model` 投影剩余次数和 token。宿主仍以发送前的持久账本做准入检查，状态字段原样只读。如果已耗尽，停止后续模型调用并保留已有工具结果、证据与失败原因。[统一预算](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-context-capability-control-design.md#62-统一预算)

### 本地文件分类服务

用已安装 PyTorch CUDA、Transformers 和 PEFT 的 Python 环境，传入本地基座和训练产物目录。训练产物包含 `encoder-adapter/`、`head.pt`、`classifier.json`。

```powershell
python apps/backend/demo/context-span-classifier.py serve --model <本地基座目录> --classifier <分类器产物目录> --port 8874
```

服务在 `127.0.0.1` 常驻模型，单个推理通道逐文件处理。`GET /healthz` 返回就绪信息，`POST /v1/chat/completions` 接受 V4 文件批次及 `task.archiveReview`。Qwen2 每个请求只编码一次共享任务前缀，各文件使用独立的前缀缓存副本，再编码文件自己的后续序列。每份文件按前缀和自己的序列核对 8,192 Token 限制。输入用量按实际编码计入 Backend 账本，分类头直接输出原句处置，生成用量为零。

在现有 `llm.profiles` 中加入以下档案，并设置 `context_organization_version` 为 `4`、`context_file_disposition_profile` 为 `local-files`。通用整理继续选择 `context_assistant_profile`。本地档案使用自己显式配置的凭据，未配置时按无鉴权请求发送。

```json
{
  "id": "local-files",
  "name": "本地文件分类",
  "provider": "custom",
  "protocol": "chat-completions",
  "model": "qwen-span-classifier",
  "base_url": "http://127.0.0.1:8874/v1",
  "max_retries": 0,
  "file_disposition_batch": { "max_spans": 128, "max_characters": 16000 }
}
```

`file_disposition_batch` 是所选 `custom`、`chat-completions` 文件档案的可选打包能力。`max_spans` 允许 1 至 256，`max_characters` 允许 256 至 65,536，后者计入每条原句和来源标记的预计负载。上面的 128 与 16,000 用于本地分类器完整文件档案。省略该能力时保持每批 32 个片段和通用字符预算。实际 Token 限制由分类器执行，换模型、供应商、协议或端点后可重新声明能力。

文件与通用材料按现有原件顺序分开投影。能满足能力声明的读取优先完整进入一个批次，V4 初筛与两种归档复核使用同一次整理启动时的文件档案快照。协议、窗口或服务失败时整批停止提交，主轮仍可读取原件，失败留在整理样本和预算账本中。

宿主为专用 V4 文件档案的同一次整理提供 `task.prefixCacheScope`，初筛和复核沿用该范围。它属于传输元数据，输出仍只有 `batch`、`choices` 和 `heading`。本地 Qwen2 服务只保留当前范围至多三个前缀，单个前缀限 2,048 Token。使用前复核精确 Token 序列和处置阶段。每个文件后续序列独立从缓存副本计算。换范围、使用无绑定请求或服务重启从空缓存开始。过长前缀仍可在单次请求内为多个文件共享。

服务的 `prompt_tokens` 记录实际编码量，按请求扣除重复编码部分。宿主的发送前预留继续按完整请求估计，持久账本同时保留预留与实际回报，不用缓存命中预支预算。缓存状态不充当来源、授权或归档证据。对照同时检查结果完全一致、局部证据回执和实际主模型效果。

已提交的文件局部处置可记录 `assessmentFingerprint`。该值由宿主从当前任务指令、用户消息身份、档案及打包配置、范围、Organizer 版本计算并随覆盖状态原子保存。会话中收到下一批材料时，仅对指纹一致的旧组复核完整工具调用、原件哈希、正文与归档回执。复核通过的旧组保留原局部投影，让出新整理批次的配额。连续覆盖按原序检查，旧组的待核对行继续留存。指纹变化、原件或回执校验失败、活动保护生效时，旧组恢复普通整理入口。此处复用的是宿主持久处置，模型继续接收新材料并使用原有输出 schema。

分多轮读取文件时，专用档案可复用完整单文件读取的处置。宿主逐片段核对该文件已有的正文或归档凭据。单文件处置通过后跳过重复评估，让后续单文件或批次得到整理机会，并沿用原文件在主轮的可见范围。局部投影的双文件见证条件不受影响。

重新评估文件工具组时，宿主从会话的持久索引核对每个原句的消息身份、字符范围和原件哈希。匹配已有归档回执的原句沿用归档，当前分类请求处理余下原句。原始回执可以继续承接局部投影。需要该归档材料时，按召回、候选和 diff 的流程加入会话文档。

专用档案开启且文件处置指纹可核对时，本轮通用窗口包含待整理杂项，或完整文件组排在窗口之后，可以单独处理完整文件组。原来的连续覆盖位置沿用旧值。只有原件经证据或归档凭据承接的局部范围才可退出主轮。下轮仍从早期待处理历史开始，经核验的旧文件处置可复用。[文件处置验收](../../v2-gap-closure-progress.md#阶段六十四验证--独立人工输入阶段)

### 文件分类训练与验收

用同一批原件分别运行两个用户任务。训练样例逐句标注当前任务所需的双方证据、明确无关的原句以及归属待核对的原句。长任务还包含前置授权与并行核查，并提及只需检查相关性的附件。同一原句换任务后可能从归档变为保留，按实际语义而非文件名或词面命中判断。读取、独立归档复核和模型标签通过真实 RuntimeLoop 导出。一个来源组的两个任务共用项目，语料准入按来源组、项目和会话检查切分。[配对语料](../../../apps/backend/test/fixtures/context-span-contrast-cases.json)

从已构建的 Backend 采集样例，再用现有语料准入工具核对每行原始导出的哈希和评审记录。分类训练读取准入后的 `train.jsonl` 与 `validation.jsonl`。既有训练集可通过 `--validation-group` 继续保留指定来源组。验收核对同批原件换任务后各条处置是否随之改变，同时核对真实主轮能读取原文、两方证据独立引用和归档可召回。[采集入口](../../../apps/backend/demo/context-span-contrast-corpus.mjs) · [训练入口](../../../apps/backend/demo/context-span-classifier.py)

## 9. 发布与验收

每次模型请求绑定角色/模式、提示词版本/hash、schema 版本、能力与 Skill 版本、文档和投影绑定、任务状态 revision、预算及原件引用。历史重放使用对应版本；宿主结果、模型提案和训练标签分开保存。

正文评审依次检查价值排序、角色分工、输入语义、决策与输出、失败保留行为。机制验收检查 schema、权限、事务、等待、恢复和消费；效果验收在相同模型、工具与任务条件下比较未压缩与整理后的实际请求，报告实体/约束/双侧证据保留、召回、下游质量与总成本。

反思、梦境、归档与训练不能读取本任务禁止的参考答案或其他隔离任务轨迹。测试与训练按项目/来源任务隔离；项目知识冻结时，评测反馈不能直接写回冻结文档。V2 Electron 的文档折叠、变量切换与重连展示单独留证。
