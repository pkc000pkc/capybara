# V2 阶段审查（Round 96）

## 当前阶段判断

当前版本已经具备可持续回归的页面闭环：工具调用、子代理结果、失败收据、artifact/evidence、会话恢复和项目应用打开/关闭/重开均能在 Electron 页面上观察到。核心功能达到“可验证原型”水准，RuntimeLoop 的 continuation 上限和自动收束路径也已通过页面验证。

## 已达到

- 工具失败能显示具体错误码和原因。
- 子任务 childId、父级委派、子级工具调用及证据引用可追踪。
- 新请求可以在上一轮失败或停止后继续执行。
- 项目应用作为独立内嵌视图可以打开、关闭并再次打开，数据保持一致。
- `npm run build` 通过，Electron 页面可启动并完成上述回归操作。

## 主要缺口

### 1. 委派状态与子任务状态没有统一分层

`delegate_task` 可以在“委派动作成功返回”的同时，让子任务内部 `read_file` 失败。页面能够展示两层事实，但父级收据的 `succeeded` 容易被误读为子任务目标成功。

### 2. Child retry gate 尚未落到 RuntimeLoop

当前重复失败保护只统计直接工具执行失败。对于 `delegate_task` 成功、子任务目标失败的嵌套路径，重试次数、child goal 签名和预算仍由模型决定。

### 3. 页面状态标签仍需更精确

页面已经保留 childId、工具调用、artifact 和 evidence，但“委派成功”“子任务失败”“父级允许重试”“父任务最终完成”还没有统一的状态分层。

## 仍未覆盖的回归场景

- 权限拒绝、能力门禁拒绝和人工确认后的恢复。
- 子代理超时、取消、父级取消和结果合并失败。
- 应用启动失败、端口冲突、托管进程崩溃后的恢复。
- Chat Completions 与 Responses API 在同一组工具调用下的页面一致性。
- 默认工具超时的实际生效值是否进入收据；当前页面只能确认是否超时，不能确认默认数值。
- 子任务收据缺失字段（`timedOut`、`exitCode`、`signal`、`processSettled`）的协议补齐。

## 开工前必须补齐的验收项

- 父级委派收据与子级目标收据分层表达，不能用单一 `succeeded` 覆盖两种状态。
- 同一 child goal 的重试预算按父任务登记，并能在页面上显示“已尝试几次 / 还剩几次”。
- 父任务完成或失败时，必须保留已有 childId、工具调用、artifact、evidence 和最后一条可验证事实。
- 人工停止与自动终止在状态协议中明确区分，并都能恢复后续会话。
- 页面回归继续覆盖：工具失败、子任务失败、父级重试、自动收束、恢复、应用重开。

## 审查结论

本阶段的主要缺口是：**嵌套委派的状态分层和 child retry gate 还没有统一落到 RuntimeLoop 状态协议中。** continuation 自动收束已经具备，下一步应把“委派动作”和“子任务目标”拆成可验证、可回放的两层状态，再继续扩展更多能力。
