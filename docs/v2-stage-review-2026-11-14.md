## 当前工作树复审（2026-11-15）

本次复审针对阶段性工作树、RuntimeLoop、Electron 主进程、Workbench 页面和新增浏览器宿主原型进行交叉检查。当前验证结果如下：

- Backend 类型检查通过，Workbench 类型检查通过。
- Backend 全量回归为 **343/343 通过**。
- Workbench 生产构建通过。
- Electron 主进程、Preload 和浏览器宿主通过语法检查。
- `browser-session-host` 与应用浏览器宿主定向测试共 **3/3 通过**。

### 已达到的阶段目标

- 项目级/系统级资源边界、上下文文档引擎、候选/证据治理、语义 diff、结构化 Runtime Envelope、确定性投影和 SQLite Trace 已有工程实现与页面证据。
- 用户指令、模型阶段摘要、工具调用、工具结果、进程状态、证据和最终回复可以在同一运行上下文中回放；项目切换、会话切换、关闭/重开和应用恢复已完成多轮页面复核。
- 文件读取、脚本执行、市场研究、行情数据、Python 分析、本地应用托管和基础行情看板已经形成可运行的产品链路。
- 失败、超时、权限门禁、停止本轮、运行差异、上下文治理和父子代理证据已经具备可观察表达。

### 本次确认的真实缺口

1. **交互式浏览器还没有接入主链路。** Backend 只向模型提供 `browser_read`；`BrowserGatewayService`/`BrowserCapabilityAdapter` 目前是独立能力契约和测试实现，`RuntimeLoopOptions` 没有浏览器宿主注入，Workbench 也没有通用浏览器工作区、地址栏、导航、点击、输入、下载或截图入口。
2. **Electron 浏览器宿主原型尚未接入 IPC。** `apps/workbench/electron/browser-session-host.cjs` 目前只存在于工作树和定向测试中，尚未被 `main.cjs`、`preload.cjs`、`workbench-bridge.ts` 或 `page.tsx` 引用；它产生的事件也没有进入 Runtime Trace/SQLite。
3. **浏览器能力状态存在语义混淆。** `main.cjs` 用本地项目应用的 `applicationBrowserHost` 作为 `browserGateway` 的可用标记，而 Backend 返回的实际含义是“受限 HTTP 页面读取”。页面上的“浏览器网关已连接”不能据此解释为交互式浏览器可用。
4. **浏览器 HTTP 入口缺少统一运行关联。** `/api/work/browser/read` 每次临时创建 HTTP executor，入口参数没有强制 `projectRef/sessionId/turnId/stepId/callId`，因此该入口的结果不能天然和通用 Browser Action、页面状态、下载产物及 Trace 统一回放。
5. **新增宿主原型存在集成前缺陷。** `browser-session-host.cjs` 的 `open()` 首次打开后，第二次用同一个 `browserInstanceId` 打开时会从 `Map` 取到 `{ view, policy }` 包装对象，却按 WebContentsView 直接调用 `setBounds/webContents.loadURL`，会导致重复打开失败。该问题尚未影响现有产品链路，因为宿主尚未接入。
6. **研究链路仍是固定源驱动。** 000682 研报 URL 在 Runtime 和页面中仍是固定集合，搜索、去重、日期范围核验、来源冲突处理和研究动作的统一 Trace 尚未收敛。
7. **异常生命周期仍缺少连续页面证据。** 应用更新失败回滚、进程异常退出、浏览器崩溃、跨项目后台实例和恢复后的未知状态还没有形成完整黑盒回归矩阵。
8. **协议收口和阶段基线仍未完成。** Backend 仍保留旧 WebSocket transport；当前工作树有约 98 个变更项且包含大量未跟踪文件，尚未形成可回滚的阶段提交或标签。

### 阶段判断

当前可以继续施工，判断为：**Runtime 最小可运行、可观测、可回放闭环已达标；产品化验收尚未达标。** 下一阶段的首要施工顺序应是：

```text
修复 BrowserSessionHost 重复打开
  → 接入 Electron IPC / Preload / Bridge
  → 将 Browser Action 接入 RuntimeLoop 与统一 Trace
  → 建立 Workbench 浏览器工作区
  → 补页面状态、下载、崩溃和恢复回归
```

本轮还确认了四个产品边界缺口：

1. 初始化器仍把系统托管 Hook/Harness 写入项目 `.capybara/hooks` 与 `.capybara/harnesses`；Round52 设置页也把 `capybara-system` Harness 标成“项目资源”。这与“系统用户 `.capybara` 保存系统能力、项目 `.capybara` 保存项目应用/会话/上下文”的目标边界不一致。
2. Electron 的 `browser_read` 只接入了受限 HTTP 页面读取；交互式 Chromium 的导航、点击、输入、下载和页面状态回放尚未接入 RuntimeLoop，因此“浏览器操作”当前仍是能力契约和应用视图的组合，尚未成为完整 Agent 能力。
3. 市场研究结果在 Workbench renderer 的 `localStorage` 中缓存，研究结果没有和项目 `.capybara` 的会话/上下文存储共用持久化源；清理浏览器数据、换用户或从另一台机器打开项目时，应用面板可能丢失研究结果显示。
4. 设置页仍会提示“项目提示词变量、项目资源目录读取失败”，且 Harness 仍按项目资源展示；这使资源治理的错误状态和系统/项目边界同时暴露在用户界面中。

因此当前阶段结论仍为：**最小可运行、可观测、可回放的桌面 Runtime 闭环已成立；产品化验收仍未通过。** 下一阶段应先收敛资源边界、资源读取错误和旧 WebSocket 契约，再处理浏览器执行器和真实应用场景验收。源评估不可变性、修正预算、训练失败重试、保存会话回放、父子代理证据表达、项目关闭/重开和侧栏恢复不再是当前阻塞项。

### 当前最重要的结构缺口

1. **资源解析存在三套语义，必须统一（P1）**

   - Electron `runtime-v2` 会无条件追加系统默认工具和 Skill。
   - Backend `ProjectResourceRegistry` 只加载 `ProjectResources.readSettings()` 返回的显式列表；空项目配置写入 `tools/files/manifest.json` 和 `skills: []`，并且初始化器会把文件工具复制进项目。
   - Backend `RuntimeLoop` 也直接使用 `config.tools` 与 `config.skills`，没有复用 Electron 的默认追加逻辑。

   结果是：设置页面看到的目录、Backend 资源 API 返回的目录、实际聊天运行时加载的目录可能不是同一个“有效资源集合”。这会造成“页面显示没有 Skill，但 Agent 实际能用”或“页面标为项目资源，运行时走系统回退”的产品级歧义。

2. **资源目录的优先级和来源尚未成为统一协议（P1）**

   现在已经能显示 `来源：项目资源/系统回退`，但还没有统一的有效项模型来表达同名覆盖、被隐藏项、最终生效项和资源来源。`source` 仍由不同注册器分别推导，不能保证 Runtime、设置页面和治理视图一致。

3. **项目切换的异步状态缺少请求绑定（P1）**

   `loadProjectResources(ref)` 返回后直接写入全局 `catalog`、变量和状态栏。用户快速切换项目或重开设置时，旧请求可能晚于新请求完成，导致页面短暂或持续显示另一个项目的资源。这是 Round 46 最需要用页面回归确认的实现缺口。

4. **空项目初始化仍把系统托管工具复制成项目文件（P1）**

   这与“系统用户 `.capybara` 托管系统工具，项目只保存项目资源”的产品边界不一致。即使复制后的运行结果可用，来源、升级、删除和同名覆盖都会产生双份事实来源。

5. **自动化测试基线仍未收敛（P1）**

1. **超时证据协议不一致（P0）**：`timed_out`、`exit_code`、`signal`、耗时、进程收束结果没有在同一条可回放收据中稳定呈现；模型不能在缺少收据时宣称“已验证”。
2. **子代理证据不能独立校验（P1）**：父任务能看到 childId 和子代理自述，但缺少父级可引用的工具结果、证据引用和合并关系。
3. **执行目录边界未在产品层表达（P1）**：非零退出场景使用了项目外临时目录，页面没有清楚显示这是临时执行目录、是否经过能力门禁，以及结果如何归属项目。
4. **应用面板尚未完成黑盒验收（P1）**：应用控制入口存在，但本轮右侧面板的可见性和滚动定位不稳定，无法证明实例状态、浏览器视图状态和更新回滚状态一致。
5. **菜单和资源治理仍有产品语义缺口（P1/P2）**：部分入口仍是占位反馈；项目/系统资源来源、覆盖关系和重复项需要在界面中明确表达。
6. **运行上下文仍偏摘要（P1）**：时间线、进程、子智能体可浏览，但候选、证据、receipt、diff 没有同等粒度的独立展开、筛选和复制入口。

## 结论

当前工作已经达到“可以继续施工”的水平，但还没有达到“产品化验收”的水平。

现阶段最重要的事实是：Electron 主进程直托管、项目目录登记、会话恢复、项目应用托管、内嵌浏览器和 Runtime Trace 已经形成可运行闭环；剩余问题主要集中在产品语义没有收敛、若干菜单仍是占位入口、上下文治理信息没有完整可视化，以及资源来源去重/优先级没有在界面中表达。

## 页面回归中确认的问题

### P0：发送和核心运行链路

核心发送链路在既有回归中已经通过：输入框唯一、点击发送只产生一条用户消息、助手结果和错误状态可见、Ctrl+Enter 路径已覆盖。

当前新建空会话在页面上能正常创建，但“快速连续点击新会话”“发送过程中切换会话”“运行中切换项目”的组合场景仍需要纳入下一轮专门验收。

### P1/P2：菜单入口与实际行为仍有少量不一致

已具备实际行为的入口包括：项目打开、新会话、项目应用、项目侧栏、深色外观、关于、协作任务/进程管理/本地运行与恢复、项目资源和设置；其中后三类运行入口统一打开运行上下文，资源和设置统一打开项目控制面。

仍会落入占位反馈的入口是“项目文件”“导出项目快照”“定时与触发”“能力演化”和“Token 用量”。这些入口需要补齐对应页面或明确空状态，否则菜单表面上显示完整，用户点击后却无法形成可执行闭环。

### P1：设置中的资源去重与来源表达不足

设置面板目前能看到：

- `project-files · tool`
- `project-files · skill`
- 两条 `capybara-system · harness`

重复 harness 是当前可见缺陷。资源目录合并需要按稳定身份去重，并保留项目优先、系统回退和同名覆盖的来源信息。页面至少要显示：

- 来源：项目 / 系统
- 是否覆盖
- 生效项
- 被隐藏或被替代的项
- 资源 revision

否则用户无法判断“项目找不到时回退系统”的机制是否真的按预期运行。

### P1：运行上下文的治理信息只有摘要，没有完整浏览入口

运行上下文已经接收候选、证据、receipt、review receipt 和 scope 数据，但页面当前只把它们显示为计数和少量待审核候选行：

- 时间线、进程、子智能体是可切换的三个页签。
- 候选、证据、应用收据没有独立可浏览的页签。
- 冲突、证据引用、diff、receipt 的详情不能按条目筛选和展开。
- 运行失败时可以看到错误，但还缺少按 `turnId / stepId / callId` 的检索和复制入口。

这意味着“能回放”已经有基础，但“可验证、可定位、可审查”还不完整。

### P1：应用状态和浏览器视图状态仍然分离

当前能看到应用进程的 running/healthy，也能打开和关闭浏览器视图，但还没有完整表达：

- 进程仍在运行、视图已关闭；
- 进程已经退出、旧地址失效；
- 项目切换后旧视图是否被安全关闭；
- 重启后浏览器视图是否应该自动恢复；
- 更新失败后版本和实例如何回滚。

应用面板需要把“实例状态”和“视图状态”显式分成两个状态轴，并给出恢复动作。

### P1：项目搜索与项目生命周期语义需要收敛

已经支持历史项目登记和不存在项目过滤，但仍需明确：

- 搜索命中项目名称时是否显示该项目下所有会话；
- 搜索命中会话首句时是否仅显示命中的会话；
- 关闭项目后其会话是否从当前侧栏消失但保留在系统登记中；
- 删除或移动目录后的历史登记如何提示；
- 多项目之间的 Runtime、应用实例和输入草稿如何隔离。

## 运行时层仍需关注的真实风险

### 1. 运行轮次和训练边界还没有全绿

既有 backend 回归为 342 项中 330 通过、12 失败。失败集中在：

- 新增上下文 hook 导致 fixture 断言漂移；
- 模型轮次/压缩轮次变化导致调用数断言过期；
- OpenAI 兼容配置的 deep-equal 期望过期；
- training failed/retry、不可变源评估和修正 token 预算边界不一致。

这不阻塞当前桌面最小闭环，但阻塞“协议与训练层全绿验收”。

### 2. 真实异常场景还缺黑盒证据

目前页面层仍缺少以下闭环证据：

- 工具超时；
- 脚本进程非零退出；
- 浏览器页面读取失败后的替代来源；
- 运行中断线重连；
- 子智能体真实委派和父代理合并；
- 应用更新失败后的回滚；
- 项目切换时后台进程清理。

### 3. 市场研究、应用版本、证据和会话还不是同一实体模型

市场研究结果主要通过会话 trace 和缓存表达，一般项目应用主要通过 manifest/instance 表达。两套状态都能恢复，但还缺统一索引，使以下关系可直接查询：

`session → turn → evidence → artifact → application version → running instance`

这会影响研究结果、看板版本、来源资料和最终回复之间的可追溯性。

## 建议的下一阶段顺序
