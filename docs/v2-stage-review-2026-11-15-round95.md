# V2 阶段性工作审查（Round95）

日期：2026-11-15

## 本轮确认

应用托管显示和子代理失败页面都进行了真实验证。项目应用在运行实例为“已停止”时仍可以打开已发布内容，关闭后能够重新加载；子代理工具错误、参数、耗时和结果都进入时间线，但父运行时未能在失败后收束。

## 已确认能力

- 已发布项目应用可在内嵌视图中打开并渲染真实看板内容。
- 关闭应用视图后可以再次打开，且运行实例状态与视图状态保持一致。
- 运行实例停止时，页面没有把已发布内容误报成正在运行。
- 子代理的工具调用失败收据可见，包含工具名、参数、`callId`、`stepId`、错误码、错误消息、耗时和 artifact。
- 手动停止异常循环后，新的无工具请求可以正常完成。

## 最高优先级缺口：失败后的父任务循环门禁

当子代理只读读取不存在文件并返回 `RUNNER_FAILED / ENOENT` 后，父任务没有将失败传播为终态，也没有按“失败后停止”收束，而是连续重新调用 `delegate_task`，页面累计到 12 次工具调用和 18 步，最终依赖人工点击“停止本轮”。

这暴露出四个运行时缺口：

1. 子任务失败没有形成父任务的确定性失败状态。
2. 相同失败事实没有阻止重复委派。
3. Tool Round / model loop 缺少最大轮次或重复动作门禁的可见收据。
4. 人工停止后缺少父任务最终摘要，`childId`、失败原因和停止原因没有统一汇总。

这是当前最影响产品可靠性的缺口，优先级高于继续扩展子代理异常场景。

## 仍需补齐的阶段缺口

### 运行时可审计性

- 默认 timeout 的实际生效值和配置来源仍未进入收据。
- `RUNNER_FAILED` 仍覆盖多个不同失败原因，缺少稳定分类字段。
- 父子任务的 `childId` 口径和最终汇总仍不统一。

### 失败与权限治理

- 能力门禁拒绝尚未完成页面验收。
- 子代理超时、取消、合并失败需要在修复循环门禁后重新测试。
- 人工停止后的父任务应产生明确的 `cancelled` 或 `stopped` 终态，而不是仅停留在会话卡片计数。

### 应用运行治理

- 已验证停止态下的打开和重新打开。
- 应用启动失败、端口冲突、托管进程异常退出和重启仍未覆盖。
- 多组同类 artifact 的去重和版本状态迁移仍需清理和验收。

## 阶段判断

文件工具、路径安全、超时可见性、A2A 成功链路、应用内嵌打开/关闭/重开已经达到可演示水平。当前不能把“子代理闭环完成”作为结论；父任务失败收束、重复委派防护和停止终态是下一阶段的阻断项。修复并通过一轮页面回归后，再继续测试子代理超时、取消、权限拒绝和应用启动异常。
