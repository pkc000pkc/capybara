# 上下文智能模型与语义压缩设计记录

## 1. 文档目的

本文记录 Capybara V2 中“上下文智能模型”的技术设想。该模型负责把上下文 Markdown、消息、工具结果和缓存信息整理成结构化、可阅读、低 token 消耗的上下文文档，并生成归档、召回、合并和语义 diff 建议。

本设计针对本地 6GB 显存（NVIDIA RTX 3060）环境，目标是验证小参数模型是否能够承担上下文治理任务。它不负责替代通用大模型完成最终业务推理。

## 2. 核心判断

模型的主要任务不是压缩文字，而是把非结构化信息转换成可维护的语义文档：

```text
消息 / 工具结果 / 网页片段 / 缓存
        ↓
实体、事件、事实、约束、状态、关系
        ↓
去重、合并、排序、冲突显式化
        ↓
结构化上下文文档
        ↓
当前任务投影 / 长期记忆
```

目标是：

> 在不损失任务相关语义、证据和可恢复性的前提下，把高噪声输入转换成更短、更稳定、更容易被模型读取的上下文文档。

## 3. 系统边界

```text
上下文智能模型：理解、分类、结构化、生成候选 diff 和归档/召回建议
Runtime：校验 revision、hash、证据、权限、冲突、幂等性和状态迁移
ContextDocument：保存当前信息、候选、证据、消息索引和版本
Archive：保存可恢复的长期记忆
Projection：为当前任务生成有限长度的模型上下文
通用大模型：执行复杂任务推理和最终用户交互
```

模型不能直接修改 Markdown，也不能直接提交事实。模型输出必须转换为结构化协议，并经过 Runtime 门禁。

## 4. 归档和召回语义

“移出”定义为归档，而不是删除。归档内容仍保留原始来源、时间、证据、版本和内容 hash，可以在需要时召回。

```text
active      当前信息区，可进入当前投影
archived    长期记忆，可被召回
candidate   已召回但尚未重新确认
```

召回状态流转：

```text
archived → recalled_candidate → accepted → active
```

如果召回内容与当前证据不一致，则进入：

```text
archived → recalled_candidate → stale / conflict
```

归档和召回都使用语义 diff，不能通过直接重写 Markdown 完成。

## 5. 算法目标

算法目标按优先级排列：

### 5.1 正确性硬约束

- 不丢失已确认事实的来源和证据。
- 不把候选、推断或过期记忆提升为事实。
- 不混淆实体、时间、任务或状态。
- 不破坏用户目标、约束、未完成事项和权限信息。
- 每次归档、召回和合并都可追溯、可逆、可重放。
- 冲突必须显式保留，不能静默选择一个版本。

### 5.2 任务保持能力

归档之后，当前投影仍需支持通用大模型完成任务。应保护：

- 当前用户目标；
- 当前约束；
- 已确认事实；
- 未完成事项；
- 工具结果和失败信息；
- 重要实体关系；
- 等待和后续观察状态。

归档候选应进行反事实检查：比较归档前后的投影，并验证任务质量没有超过允许阈值的下降。

### 5.3 上下文效率

在满足正确性和任务保持之后，优化：

- 当前投影长度；
- 信息重复度；
- 过期信息比例；
- 推理负担；
- 召回成本。

目标不是单纯最小化 token，而是提高“任务相关信息密度 / 上下文成本”。

### 5.4 长期记忆质量

归档记录应支持按实体、事件、时间、主题和语义相似度召回，并能识别新旧版本、过期内容和冲突内容。

## 6. 文档化输出

结构化上下文文档应至少表达：

- 实体；
- 已确认事实；
- 当前状态；
- 时间和来源；
- 证据引用；
- 冲突和未知；
- 未完成事项；
- 后续行动。

示例：

```markdown
## 客户：Acme

### 已确认事实
- 客户已支付订单 1024。
  - 来源：工具调用 call-18
  - 时间：2026-11-04
  - 证据：artifact-91

### 当前状态
- 退款请求仍在处理中。

### 冲突与未知
- 邮件金额为 120 美元，账单金额为 125 美元。
- 最终金额尚未确认。

### 后续事项
- 等待支付系统回调。
```

## 7. 模型操作集合

第一版限制为有限操作集合：

```text
extract_fact
normalize_entity
merge_duplicate
separate_conflict
summarize_event
update_state
archive_section
recall_memory
request_evidence
propose_diff
```

示例结构化输出：

```json
{
  "operations": [
    {
      "op": "archive_entry",
      "targetId": "info-42",
      "reason": "已被最新状态覆盖",
      "recallKeys": ["退款", "订单1024"],
      "evidenceRefs": ["e-91"],
      "confidence": 0.92
    }
  ]
}
```

每个变更应带有 `documentId`、`baseRevision`、`targetId`、`expectedHash`、`evidenceRefs`、`reasonCode`、`confidence`、`risk` 和 `idempotencyKey`。

## 8. 长上下文处理

小模型不一次读取完整文档，而使用分层处理：

```text
完整 ContextDocument
        ↓
按 section / entry / candidate 分块
        ↓
局部编码和摘要
        ↓
任务相关召回
        ↓
候选变更生成
        ↓
全局一致性检查
```

推荐维护多级表示：

```text
原始证据 → 信息条目 → 章节摘要 → 文档摘要 → 当前任务投影
```

每一级都必须保留来源 ID，使摘要可以回指原始证据。

## 9. 6GB 显存下的实现策略

推荐配置：

- 0.5B–3B 参数的基座模型；
- 4-bit 量化推理；
- QLoRA / LoRA 微调；
- 1K–4K token 的短窗口训练样本；
- gradient checkpointing；
- 小 batch 加梯度累积；
- 必要时 CPU offload；
- 长上下文通过分块、索引、摘要和召回实现。

训练目标限定为上下文治理，不训练通用 Agent。模型主要学习：

- 信息抽取；
- 实体归一化；
- 重复检测；
- 冲突识别；
- 结构化文档生成；
- 归档判断；
- 记忆召回排序；
- 语义 diff 生成。

## 10. 训练样本

训练样本采用短输入和结构化目标：

```text
输入：
  当前文档片段
  新消息或工具结果
  相关缓存片段

输出：
  结构化事实
  候选状态
  diff 操作
  证据引用
  归档理由
```

重点收集：

- 可合并的重复信息；
- 不能合并的相似实体；
- 新旧状态冲突；
- 可归档但必须保留召回线索的信息；
- 归档后仍需保留的约束；
- 召回后需要重新确认的记忆。

训练标签应来自 ContextDocument 的状态变化和任务结果，而不是单纯的 Markdown 改写：

```text
原始 ContextDocument
→ 确认的归档结果
→ 后续任务表现
→ 召回与合并结果
```

## 11. 结构化输出稳定性

结构化输出采用三层保障：

```text
模型训练固定任务和 schema
        ↓
JSON Schema / grammar constrained decoding
        ↓
Runtime Typed Envelope 和字段校验
```

解析失败最多进行有限次修复；仍失败时生成 `no-op` 或 `request_review`，不能让模型直接修改上下文。

## 12. 验证指标

需要分别评估：

### 文档质量

- 事实抽取准确率；
- 实体归一化准确率；
- 重复合并准确率；
- 冲突识别召回率；
- 来源和证据保留率；
- 人工可读性评分。

### 压缩质量

- token 压缩率；
- 任务相关信息保留率；
- 重复内容减少率；
- 关键约束保留率。

### 归档质量

- 错误归档率；
- 归档后任务性能下降；
- 召回准确率；
- 召回延迟；
- 召回后的合并成功率。

### 协议质量

- 结构化输出解析成功率；
- diff 应用成功率；
- revision/hash 冲突拦截率；
- 幂等重放正确率。

## 13. 推荐研发顺序

```text
第一步：结构化抽取和文档生成
第二步：候选 diff 和证据绑定
第三步：重复合并与冲突识别
第四步：可逆归档
第五步：记忆召回和候选恢复
第六步：反事实投影评估
第七步：针对实际任务优化模型
```

第一阶段不让模型直接决定最终归档，Runtime 和规则层负责安全审核。模型稳定后，再逐步扩大自动化范围。

## 14. 当前设计结论

在 6GB RTX 3060 环境下，该设想技术上可行，前提是：

1. 使用小参数模型作为上下文治理模型；
2. 采用分块和层级文档处理超长上下文；
3. 把移出定义为可召回归档；
4. 用结构化 diff 表达所有状态变化；
5. 由 Runtime 执行确定性校验和提交；
6. 用任务质量验证归档和压缩结果；
7. 把通用大模型保留为最终任务推理层。

这份文档记录的是设计目标和技术路线，后续实现应以实验数据校正模型规模、窗口长度、归档阈值和自动化等级。
