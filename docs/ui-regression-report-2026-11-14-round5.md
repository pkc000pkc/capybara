## H04：编写并运行 Python 分析

**结果：失败，缺陷 R5-01。**

Agent 在页面中明确说明当前会话只激活了两个系统 harness（`hook-authoring`、`variable-authoring`），没有可调用的写文件、执行 Python 或读取行情数据工具，因此没有生成脚本、启动进程或返回 stdout/退出码。

代码审查与页面现象一致：项目初始化把 `tools/files/manifest.json` 放入工具目录，但 RuntimeLoop 初始 `tools.items` 为空，工具只进入 catalog，需模型先搜索并加载资源后才会进入模型工具定义。当前模型没有稳定完成这一步，导致产品目标“编写和执行代码”无法从普通用户请求直接达成。

## 当前缺口排序

### P0：普通请求不能稳定得到文件和 Python 能力（R5-01）

需要把“项目优先、系统回退”的工具目录与“当前可调用工具”打通：启动时至少能显示可用能力，或由 Runtime 在识别到编程任务后自动提出并完成受控加载。工具加载必须留下来源、权限和版本证据。

### P0：浏览器研究结果的上下文预算治理不足

HTTP 404、重复 artifact 回读和长工具结果仍可能把模型输入推过上限。需要在工具结果进入下一轮前做摘要、分页上限、重复读取抑制和预算预警，并在可替代来源存在时切换来源。

### P1：应用实例 ID、健康检查和右侧面板状态不一致（R5-02）

发布/启动返回的实例标识必须成为后续 `health_check`、停止、重启和 UI 面板的唯一 ID；不能让 `v1` 这种版本号被误当成运行实例 ID。

### P1：隔离区产物没有完成可用性闭环

研报下载已有字节数和哈希，但缺少校验、全文解析、标题/发布日期确认及从 `quarantined` 到 `verified` 的可见状态迁移。

### P1：组合能力没有严格收敛到用户请求范围

H02 只要求下载研报，但返回中同时执行并展示了行情获取、Python 分析和看板发布/打开步骤。结果虽然可追溯，但扩大了任务范围，增加了耗时、上下文和副作用面。组合能力需要支持明确的步骤选择，未被请求的步骤不能默认执行。

### P1：业务结果与项目应用状态的双向同步仍需回归

H05 证明页面可访问，但右侧面板没有跟随工具启动结果更新。还需要验证应用停止、重启、关闭项目、重新打开项目后的实例恢复和历史回放。

## 阶段结论

本阶段已经达到“可运行、可观测、可回放”的基础水平：会话、工具时间线、证据、Python 结果、看板页面和交易建议可以关联起来，失败后也能恢复。
