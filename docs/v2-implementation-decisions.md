# Capybara V2 Implementation Decisions

This file records implementation decisions made while converting the V2 design into the system runtime. It is part of the system project and must not be confused with the separate Gaia2 work project at `D:/gitlocals/capybara-test-workspaces/gaia2-v2-work`.

Requirement-by-requirement evidence is summarized in `docs/v2-completion-audit.md`.

## 2026-11-17 — Context, capabilities, control and prompt design alignment

The current review baseline is [V2 context, capability, control and prompt design](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/v2-context-capability-control-design.md). It consolidates 20 gaps with current evidence and acceptance scenarios. These are design requirements; existing mechanism tests do not establish that the complete flow meets them.

- `session_context` is the canonical design name for the working session document; existing code and samples also use `context`. `project_context` holds project-scoped, cross-session memory. Both documents retain stable identities and revisions and receive governed local diffs.
- Historical messages remain in the original trace. Their model-request projection can shrink only after the corresponding information has durable document receipts. A seen-message cursor is not a coverage frontier.
- `runtime_state` owns tasks, plans, actions, waits, human requests and children. Document summaries reference that state; document diffs cannot grant authority or change execution state.
- Tool catalogs, request-local schema projection and dispatch permissions are separate. Skills describe methods and dependencies; neither Skill text nor tool visibility grants execution permission.
- The [prompt drafts](D:/gitlocals/kanli8-human/capybara-github/capybara/docs/prompts/v2/README.md) adapt Claude's memory organization and execution discipline to these boundaries. The proposed version 2 Envelope requires its paired schema and runtime gates; current version 1 compatibility is separate evidence.

## 2026-11-03 — System/work-project boundary

- System changes live under `apps/`, `packages/`, and system-level `docs/`.
- Gaia2 adapters, fixtures, datasets, and benchmark launchers remain in the separate Gaia2 work project; they are not copied into the system runtime.
- The V2 runtime provides the context, candidate, evidence, diff, projection, reflection, memory, and A2A mechanisms. A project supplies project content, tools, and domain configuration.

## 2026-11-03 — Canonical context representation

- The persisted source of truth is a structured `ContextDocument`.
- Markdown is the human-readable serialization and model projection format.
- Stable hidden markers identify the five sections and information entries. A parser rejects duplicate, missing, or malformed markers instead of guessing.

## 2026-11-03 — First runtime slice

- The initial system slice is implemented as `ContextDocumentEngine` in `apps/backend/src/core/context-document-engine.ts`.
- It provides five-section documents, Candidate and Evidence records, revision-bound DiffProposal application, entry-hash conflict checks, idempotent ApplyReceipt values, and deterministic Projection values.
- The engine is intentionally independent of project Hooks so it can be called by the system RuntimeLoop.
- Markdown parsing reconstructs information entries and candidate blocks from stable markers; malformed or duplicate section markers fail closed. A document metadata marker preserves document identity, session, project, constitution revision, cursor, and revision across serialize/parse.

## 2026-11-11 — Project context persistence and model projection

- `project_context` is a real project-scoped `ContextDocument`, persisted under `.capybara/project_context.json` with a Markdown sidecar at `.capybara/project_context.md`. The JSON state retains receipts and projection bindings; the Markdown sidecar is the human-readable serialization.
- RuntimeLoop loads the project document when a session starts and exposes its identity and revision through `projectContextDocument` and `contextScopes`. A new RuntimeLoop for the same project reads the same document identity and revision.
- Project and session projections are separate. The model-facing projection reserves a bounded portion of the input budget for project context and keeps the session projection separately bound. Project diff proposals carry `scope: project` and use the project document revision and projection gates.
- System-owned `context-organization` Hooks receive bounded project/session projections and runtime cache data. They may return only governed `contextProposals`; RuntimeLoop converts them into ordinary revision, evidence, projection, idempotency, and project-write checks before applying them.
- Training samples now retain the serialized project context and revision alongside the session context, normalized candidate cache, raw runtime cache, raw LLM messages, and the rendered project system prompt. The system constitution remains a runtime control input and is not confused with the captured project prompt.

## 2026-11-16 — Training closure and memory boundary

- Training samples use `schemaVersion: 2` and retain apply receipts, candidate/evidence reviews, archive records, recall records, rejection reasons, and preserved conflict evidence. Valid samples convert directly to `{ input, target }` JSON through `toTrainableContextExample()`.
- Archive records retain the pre-archive body, heading path, source candidates, evidence references, operation, and result. Archived information is searchable through `recallArchivedInformation()` and is emitted as a separate archive result; it is not silently promoted into active information.
- `runtime.context.v2.project` accepts `includeStatuses` so an accepted candidate can still author a governed archive proposal. The archive operation remains bound to the current projection, revision, candidate, evidence, and receipt gates.
- Recall currently has discovery semantics: it emits candidate/archive results and records the recall in training data. A recall result does not yet mutate the active document or automatically appear in the next model projection; any re-entry must be represented by a normal observation/proposal path.
- Conflict-preservation samples require separate supporting and contradicting evidence references. A single collapsed evidence list is rejected by the training-sample validator rather than being treated as a trainable conflict label.
- Candidate placement carries `durability`, `target`, `confidence`, `reason`, and `projectAnchors`. RuntimeLoop rejects project observations and proposals without project durability, a project target, valid project anchors, and evidence. Session-only or transient classifications remain outside `project_context`.
- Project anchor authenticity is checked at the RuntimeLoop boundary: file-like anchors must resolve within the current project directory, artifact anchors must match evidence, and explicit anchors require message/artifact/external evidence. A Session candidate can be promoted into Project scope only when this check passes; RuntimeLoop copies compatible evidence, creates the Project Candidate, rebinds the proposal to a fresh Project Projection, and then applies the ordinary semantic-diff gates.

## 2026-11-03 — Conflict and idempotency policy

- A proposal with a stale document revision returns `CONTEXT_REVISION_CONFLICT` and does not mutate the document.
- A proposal with a stale target entry hash returns `ENTRY_HASH_CONFLICT` and does not mutate the document.
- Reusing an idempotency key returns the original receipt and does not create a second revision.
- Runtime state export persists the document together with the idempotency-key/receipt map, so a restored loop cannot replay an already applied proposal.
- A semantic proposal is bound to the projection ID and content hash used to author it. The engine remembers projection bindings in runtime state and rejects missing, stale-revision, or hash-mismatched projections before candidate lookup or mutation.
- The RuntimeLoop seeds the V2 system/tools sections from the rendered project prompt and active tool catalog, and refreshes the message section before a V2 projection or apply operation. The project still controls its prompt and tools; the system controls their projection and governance.
- The fixed constitution is versioned as `constitution-v2.1` in `apps/backend/src/core/v2-prompts.ts`; the project-rendered system prompt is appended as a separately identifiable section so projects remain customizable without changing the system constitution.
- The prompt family is kept in one versioned system module with separate Constitution, Runtime, Candidate Normalize, Evidence Review, Reflection, Dream, Memory Recall, A2A Child, Parent Merge, and Final Response constants. RuntimeLoop owns the active constitution/project projection; auxiliary prompts remain constrained instructions for their respective governed stages.
- Before each model step, RuntimeLoop builds a bounded deterministic V2 projection and uses it as the model's system message, while retaining the structured LLM tool-call history for provider pairing and replay. The projection binding ID/hash is included in the model-visible context for proposal authorship.
- The projection budget is calculated after reserving the structured history and tool definitions, so V2 context does not consume the whole V1 model window merely by duplicating provider-facing history.
- Runtime integration is covered by `apps/backend/test/context-document-runtime.test.ts`: a V2 projection event is emitted and the projection binding survives RuntimeLoop state export and restore.
- Candidate governance has an explicit `runtime.context.v2.review` command and `CandidateReviewReceipt`. Rejection/quarantine statuses may be recorded with a reason; acceptance still requires evidence, and every review uses the document revision gate.
- Candidate, evidence, and evidence-attachment mutations advance the same document revision as information writes. Review receipts are persisted beside ApplyReceipt values and restored with the document.
- Review commands bind `documentId` before changing candidate state. Applying a proposal against a rejected, stale, irrelevant, or superseded candidate is rejected rather than silently promoting it.
- `ContextDocumentEngine.observe()` is the system observation boundary; it preserves source metadata, creates the Candidate/Evidence chain, and deduplicates repeated observation IDs. `propose()` binds a candidate proposal to a registered projection and current revision. Memory recall searches both memory candidates and archived information, returns deterministic match reasons, and child-agent results enter through an explicit child-agent source.
- Projection fitting is deterministic and entity/section bounded. `sourceEntryIds`, `sourceCandidateIds`, `selectionReasons`, and `truncatedSections` describe only content actually selected; the projection never slices through an arbitrary Markdown character boundary.
- Context section content, message cursors, and session identity are revisioned mutations. A projection authored before a system/tool/message change therefore fails the normal revision gate; the model-visible projection comment carries the bound document revision without making the fixed runtime prompt self-mutating.
- Evidence records are serialized as a hidden metadata marker in the candidates region and restored before candidate references are validated. Candidate creation and observation reject unknown evidence references; repeated observations merge newly observed evidence instead of silently losing it.
- Projection ordering uses code-point comparison and projection IDs are derived from document identity, revision, profile, and content hash. The Markdown and content hash are stable for the same document state and profile; timestamps remain receipt metadata only.
- Candidate projection ordering uses captured observation time followed by candidate ID. This keeps paginated tool observations in capture order while preserving deterministic tie-breaking, so a bounded projection does not reorder pages by random UUID.
- A deduplicated observation returns the post-merge candidate snapshot, including evidence attached during that observation. This keeps the observation result aligned with the persisted document after evidence reconciliation.
- Projection fitting treats the character budget as a hard upper bound, including section omission markers. If a marker cannot fit, the section is omitted and recorded as truncated rather than exceeding the requested budget.
- Bounded projections accept an explicit `pinnedCandidateIds` priority list. The engine validates its shape, orders pinned candidates deterministically before the latest window, renders the selected candidates in canonical capture order, and records `pinned-candidate` in selection reasons. Pinning never bypasses candidate status or the character budget; it exists to preserve confirmed execution receipts through compaction.
- Runtime restoration detaches the supplied ContextDocument snapshot before validation and mutation. Checkpoint or replay callers therefore cannot mutate the live document through an object alias outside the revision and diff gates.
- Candidate metadata is validated at the engine boundary, including source identity, artifact identity, status, timestamps, and reference arrays, so malformed observations cannot enter the canonical document through a typed caller cast.
- Restored information entries must reference existing evidence, candidates, and superseded entries; unknown lineage references fail closed before the snapshot becomes live runtime state.
- Restored ContextDocument state must contain all canonical collections before field validation begins; malformed snapshots fail with a typed document error instead of throwing an unstructured runtime exception.
- The system/tools sections require runtime governance for mutation. Project prompts are labeled lower priority and the constitution states that domain prompts cannot override system protocol, permissions, evidence rules, or RuntimeLoop gates.
- Legacy V1 snapshots migrate into a new V2 document on restore: completed tool observations become tool candidates with evidence, while malformed legacy observations remain only in the original trace. Runtime checkpoints now carry the complete V2 engine state and control state, so checkpoint restore also rolls back candidate/evidence/projection state together with messages and tools.

## 2026-11-06 — Projection windows, completion receipts, and batch diffs

- The canonical candidate order remains capturedAt followed by candidate ID. A bounded projection may explicitly select candidateSelection=anchor-latest: retain the earliest user task candidate as an anchor, fill the remaining budget from newest candidates, and render the selected set back in canonical order. Selection reasons record latest-window; the default remains chronological for reproducible callers.
- RuntimeCompletionCheck.requiredActions is a typed runtime ledger reference. Allowed forms are a tool name, tool:<name>, call:<callId>, step:<stepId>, or tool:<name>#<sha256(JSON arguments)>. The finish gate counts only successful tool timeline steps and rejects unverified action claims.
- Multiple semantic diffs from one envelope share a base revision and projection binding. ContextDocumentEngine.applyBatch() validates the complete batch against the authored projection, applies it on a detached trial engine, and commits the resulting state only when every proposal succeeds. A rejected member leaves the live document and receipts unchanged.
- Gaia2 bridge observation keys are actor-scoped and same-batch capture timestamps are monotonic. The official bridge profile explicitly requests anchor-latest, while raw observations and evidence remain preserved for audit.
- Mutation receipt metadata is generated from assistant tool-call arguments and authenticated executionOutcome fields before the candidate is observed. It is bounded and only applied to write, finish, and unknown effects. This preserves entity identity through provider compaction without summarizing read results.

## Decision state

- The runtime state snapshot is the persistence boundary for ContextDocument records, receipts, and projection bindings; a storage-backed session repository can reuse that state shape.
- The RuntimeLoop command/event names are fixed as `runtime.context.v2.project`, `runtime.context.v2.apply`, `runtime.context.v2.review`, `runtime.context.v2.evidence.review`, `runtime.context.v2.memory.recall`, `runtime.context.v2.child.merge`, `runtime.context.v2.dream`, `runtime.context.v2.projection.created`, `runtime.context.v2.receipt.created`, `runtime.context.v2.candidate.reviewed`, `runtime.context.v2.evidence.reviewed`, `runtime.context.v2.memory.recalled`, `runtime.context.v2.child.merged`, and `runtime.context.v2.dream.created`.
- RuntimeLoop exposes `runtime.context.v2.observe` as the general candidate/evidence ingestion boundary. The command accepts a typed source, raw artifact ID, normalized content, and optional evidence record; it binds an optional document ID, delegates deduplication and evidence attachment to ContextDocumentEngine, advances the runtime snapshot, and emits `runtime.context.v2.observed`. Tool observations and legacy migration use the same engine boundary, so user, model, external, memory, and child-agent evidence can enter through one governed path.
- Runtime candidate metadata exposed in snapshots and observation, memory-recall, and child-merge events includes `sourceId`, `capturedAt`, and optional tool/run/step bindings. This keeps provenance visible to clients without exposing the full normalized candidate body outside the governed document/projection path.
- Memory recall is read-only and returns candidate metadata with a deterministic reason. Child merge is the parent-owned A2A boundary; it accepts source-bound child results into the candidate section and still requires the ordinary evidence and diff gates before information writes.
- Model control output may carry a versioned `RuntimeEnvelope` beside the legacy status/content response. The parser validates decisions, actions, candidate diffs, evidence requests, uncertainties, wait specifications, and completion checks; a `finish` envelope requires a verified completion check and session/run binding.
- Interactive envelope decisions are structurally complete: `wait` requires a wait specification, `ask_user` requires an explicit question action, and evidence request source kinds are typed before any control state is persisted.
- Envelope candidate diffs are required to carry evidence, validate operation-specific fields, and bind optional target hashes; `finish` requires a verified completion check during parsing as well as the runtime gate.
- A `propose_diff` RuntimeEnvelope is converted into model-actor `runtime.context.v2.apply` proposals inside RuntimeLoop, so the model cannot mutate the document outside the existing projection, evidence, revision, idempotency, and receipt gates. The other envelope decisions remain observable protocol decisions and continue through the existing tool/loop state machine.
- A `wait` RuntimeEnvelope requires a `waitSpec`, stores the envelope on the model step, pauses the loop after scheduling its continuation, and resumes through the existing `run.resume` path. Provider-native tool calls remain the only executable tool channel; envelope tool actions are rejected to prevent a second side-effect path.
- Evidence review is a separate parent-owned command/event pair, `runtime.context.v2.evidence.review` / `runtime.context.v2.evidence.reviewed`. It records supporting/contradicting evidence, target entries, rationale, and review revision; `needs_more_evidence` leaves the candidate pending, while accept/reject/conflict uses the candidate revision gate.
- Evidence review and semantic diffs bind every cited evidence ID to the target candidate. A globally valid evidence record cannot be borrowed to promote an unrelated candidate.
- `replace_body` preserves information lineage by marking the prior entry `superseded` and creating a new active entry with `supersedesEntryIds`; Markdown metadata round-trips this relation.
- Pending V2 control state is persisted in the RuntimeLoop snapshot. `wait`, `ask_user`, and evidence requests pause the loop with resumable state; a non-auto-start user message clears the pending control state and resumes the run, while reflection attempts are bounded to three.
- Dream is scheduled on loop completion and is also callable through `runtime.context.v2.dream`. It only creates a deterministic `context-diff` plan for duplicate/stale/pending candidates; applying any resulting change still requires ordinary evidence review and semantic diff gates.
- The Gaia2 adapter boundary is fixed in `src/capybara_v2_adapter.mjs`; it emits project/apply/review, memory-recall, and child-merge envelopes while leaving state transitions in the system. The validated mechanism slice is `v2-mechanism-smoke`, with official score reporting kept separate.
