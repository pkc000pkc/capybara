# V2 DAG 与模型请求边界讨论记录

版本：v0.1 · 日期：2026-11-24

## 1. 讨论结论

DAG 的首要目标是减少大模型请求频次，把可由代码、规则和已授权工具确定完成的工作编译为一次运行内的执行图。模型负责理解目标、生成高层计划、处理无法规则化的语义判断和交付最终答复。RuntimeLoop 负责校验、调度、证据和完成门禁。

```text
目标理解
  ↓ 一次模型请求
高层执行图
  ↓ RuntimeLoop 编译
工具、转换、循环、断言和验证节点
  ↓ 代码与规则执行
局部语义判断或异常恢复
  ↓ 受控模型请求
最终结果与证据
```

DAG 不是把模型的每一步思考转成节点，也不是把所有信息裁决交给规则。它把确定性部分显式化，把真正需要语义判断的边界保留下来。

## 2. 为什么能降低请求频次

传统循环会在“取一条数据、判断一条数据、再取下一条数据”之间反复请求模型。DAG 将集合处理移到一次编译后的执行图中：

- 工具节点读取外部状态并保存原始 artifact。
- `filter`、`map`、`flat_map`、`sort`、`dedupe`、`group_by`、`partition`、`paginate`、`reduce` 和 `normalize` 由代码执行。
- `foreach` 只按有界集合展开工具节点，不为每个元素重新生成计划。
- `assert` 负责结构化状态、数值和完成条件的规则验证。
- 无法从结构化输入可靠判断的内容单独进入语义边界。

因此模型请求数由“数据条目数”转为“计划、语义边界、恢复和最终答复”的数量。

## 3. 节点分类与请求边界

| 节点类型 | 处理者 | 是否触发模型请求 | 典型工作 |
| --- | --- | --- | --- |
| `tool` | RuntimeLoop 与授权工具 | 否 | 读取应用状态、文件、MCP 或已授权服务 |
| `filter` | 代码与 JSONata | 否 | 过滤记录 |
| `transform` | 代码与 JSONata | 否 | 映射、规范化、排序、去重、分组、分页、聚合 |
| `foreach` | RuntimeLoop | 否 | 对有界集合展开同一工具调用 |
| `assert` | 规则引擎 | 否 | 状态、数量、数值和完成条件检查 |
| `semantic` | 模型 | 是 | 规则无法表达的分类、语义归因和局部判断 |
| `write` | RuntimeLoop 与授权工具 | 否 | 外部副作用，必须绑定验证节点 |
| `finalize` | RuntimeLoop | 否 | 汇总节点结果、artifact、receipt 和 evidence |

模型不得隐式地在 `filter`、`foreach`、集合拼接或分页之间重新介入。若一项工作确实需要语义判断，应显式标出语义边界并单独计量。

## 4. 编译结果

`execute_workflow` 的输入先经过结构校验和引用校验，再生成编译摘要。摘要包含：

- `graphHash`，用于绑定本次定义、恢复和能力版本。
- `nodeCount` 与工具节点数量。
- 确定性节点数量。
- `foreachNodeCount` 与最大展开规模。
- 语义节点数量。
- 估算模型请求数。

当前引用必须指向前置节点，未知引用、前向引用、重复节点和超出规模的图在编译阶段拒绝。运行时 Workflow 状态、节点状态和最终 artifact 都保存编译摘要，便于验证模型请求是否被压缩。

## 5. 确定性算子合同

每个确定性算子必须满足以下条件：

1. 输入来自前置节点或当前局部绑定。
2. 执行不产生外部副作用。
3. 输出可序列化为 artifact。
4. 输出状态、输入数量、结果预览和失败原因可观察。
5. 不修改原始工具结果，只生成新的派生结果。
6. 在超时、数量和表达式长度边界内运行。

`reduce` 使用显式累加器，`paginate` 使用有界页大小，`foreach` 使用 `maxItems`，`normalize` 只做结构化的空白和嵌套值整理。集合运算保留顺序和重复处理规则，不能以“结果更完整”为理由静默删除来源。

## 6. AppWorld 中的落点

退款类任务可以编译成：

```text
读取订单与邮件
  ↓
normalize
  ↓
filter 目标订单
  ↓
join 或 group_by 对齐来源
  ↓
assert 订单状态与金额字段
  ↓
semantic 仅处理邮件语义歧义
  ↓
write 执行授权动作
  ↓
tool 重新读取状态
  ↓
assert 验证最终状态
```

订单号、金额、状态、分页和重复记录不应逐条回到模型。不同来源的冲突仍由主任务模型处理，DAG 只负责把来源、字段和证据整理成可消费的结构。

## 7. 与上下文和证据的关系

DAG 节点输出进入 artifact 和 observation。工具节点保存真实回执，确定性节点保存派生 artifact，断言节点保存通过或失败的规则结果。主任务模型收到的是节点摘要、来源引用和必要的原始页，不需要把每个中间对象都复制进消息历史。

归档和上下文整理仍通过普通文档 diff 和版本门禁完成。DAG 生成的派生内容不能直接成为事实，也不能替代原始证据。语义节点产生的判断与工具观察分开保存，冲突内容保留各自来源。

## 8. 当前实现与验证信号

当前实现已经覆盖：

- Workflow 前向引用和未知引用拒绝。
- `filter`、`map`、`flat_map`、`sort`、`dedupe`、`select_fields`、`group_by`、`partition`、`paginate`、`reduce` 和 `normalize`。
- `assert` 节点及失败状态。
- `foreach` 的有界展开。
- Workflow 节点 artifact、状态、失败原因和编译摘要。
- A2A 等待屏障，父层在子任务活动期间只使用生命周期工具。
- 动作子代理的单写入者租约、结果回执和未知结果保留。

可接受的验证信号包括：

- 一次 Workflow 内完成多条记录处理，模型请求数不随记录数线性增长。
- 时间线出现 transform/assert 节点和对应 artifact。
- `RuntimeWorkflowPlan.compile` 中的 `graphHash`、节点数量和估算请求数可读取。
- 父层出现 `delegation_wait`、`delegation_review`，不会在等待阶段调用业务工具。
- 子代理结果包中存在真实工具证据和动作回执，未知副作用不会被自动重放。

## 9. 尚需独立验证的边界

- AppWorld 正式样本是否会自然生成 Workflow，而不是只执行普通工具轮。
- 语义节点的独立模型调用、输出 schema 和预算计量。
- 写入节点与验证节点的端到端绑定。
- 多工具只读节点的并发调度与资源限制。
- AppWorld 任务中图执行相对普通循环的模型请求量和准确率变化。

这些边界必须通过运行轨迹、artifact、receipt 和模型调用计数验证，不能只根据模型文本判断 DAG 已经生效。
