# V2 阶段性工作审查（Round91）

日期：2026-11-15

## 当前判断

V2 已经形成可运行、可回放、可审查的主闭环，当前可以继续做场景验收和缺口收敛。核心链路已经通过页面验证：项目与会话恢复、实时工具轨迹、文件读取、进程执行、超时收束、失败收束、项目应用发布与打开、设置与能力来源展示。

## 仍然存在的真实缺口

### 1. 运行事件关联还缺少逐项可审计证据

页面已经显示工具名、参数、耗时、结果和失败原因，但还没有完成页面级逐条核对：同一个 `turnId / stepId / callId` 是否贯穿模型阶段、工具事件、进程收据、证据记录和最终回复。当前只能确认 `callId` 在卡片中出现。

### 2. 超时分支的无效重试仍然过多

Round89 的真实超时场景中，模型先后尝试了错误的 `run_code -c`、不可用的 `python`、环境探测和最终的 `py -3`，形成 4 次工具调用、12 步才收束。运行时收据最终正确，但失败后的重试预算和工具环境探测策略仍然需要治理，否则用户会看到长时间“处理中”。

### 3. 仍未完成的失败态场景

- 能力或权限拒绝的页面闭环。
- 子智能体非空运行、子任务工具调用、父代理合并和失败回收。
- 应用启动失败、端口占用、应用进程退出后的页面状态。
- 默认 timeout 与显式 timeout 的差异。

### 4. 前端表达仍有审查负担

工具过程卡片已经可用，但历史证据治理条目数量较多，重复产物和重复动作会增加阅读负担；阶段摘要、运行上下文和最终回复之间还缺少一个可直接筛选同一任务链路的入口。

### 5. 可验证性边界需要继续保持

项目应用中的研究结论、资料来源和产物状态已经展示“待核对/待人工审查”，这是正确的。下一阶段需要确保权限拒绝、外部下载失败和应用运行异常也沿用同一套“证据、状态、原因、可恢复动作”表达，而不是退化成普通文本错误。

## 阶段结论

当前版本达到“可以开工做系统性场景验收”的水平，也达到“主链路可演示”的水平；尚未达到“所有故障态和所有关联 ID 均完成验收”的水平。下一阶段优先顺序应为：

1. 收敛超时/工具失败后的重试策略与终止条件。
2. 在运行上下文中补齐 `turnId / stepId / callId` 的可见关联。
3. 验收权限拒绝、子智能体非空、应用启动失败。
4. 对重复产物和运行事件增加聚合、筛选或折叠，降低回放阅读成本。
